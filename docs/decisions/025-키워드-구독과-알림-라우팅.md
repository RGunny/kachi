# 025. 키워드 구독과 알림 라우팅

## 배경

kachi의 목적은 "관심 키워드를 등록한 사용자에게, 그 사용자가 정한 채널로, 그 키워드의 뉴스 요약을 보내는 것"이다.

지금까지는 이 목적의 뒤 절반, 즉 수집 → 요약 → 발송 파이프라인을 먼저 만들었다. 
ADR 010이 초기 설계에서 user를 의도적으로 뺐다. 
여러 사용자가 같은 키워드를 등록해도 수집·요약은 한 번이면 되므로, 키워드 이름만 받아 ai-service의 비즈니스에 집중하고 사용자별 확장은 "user-service internal API가 user id를 제공할 때"로 미뤄 두었다. 
알림 채널은 문자·이메일이 번거로워 Slack·Discord·Telegram 세 개를 두고 관리자 수신처로 발송을 검증해 왔다.

ai-service가 요약·격리 이벤트를 자기 topic에 발행하게 되면서(ADR 023) 파이프라인의 발행 쪽은 이어졌다. 
이제 사용자와 알림을 잇는 차례다. 채널 종류와 무관하게 "누가 어떤 키워드를 어떤 채널로 받는가"를 어느 컨텍스트가 소유하고 어떻게 펼칠지 정한다.

현재 파이프라인은 이렇다.

- user-service는 `Keyword(userId, name)`을 저장한다. 사용자의 알림 채널은 아직 없다.
- 활성 키워드 internal API는 키워드 이름만, 전체 사용자에 걸쳐 중복을 제거해 내보낸다. 뒷단은 사용자를 모른다.
- collector와 ai는 그 이름 문자열로 뉴스를 수집하고 요약한다. `tesla`, `Tesla`, `테슬라`는 서로 다른 세 키워드다.
- notification-service는 `(requestId, channel, recipient)`를 받아 발송하는 실행기다. 누구에게 보낼지는 호출자가 정한다.
- ai-service는 요약·격리 이벤트를 자기 topic에 발행한다(ADR 023). 소비자는 아직 없다.

정해야 할 것은 네 가지다.

1. 구독(사용자, 키워드, 채널, 채널별 주소)을 어느 컨텍스트가 소유하는가.
2. 키워드의 identity — 같은 키워드를 여러 사용자가 등록했을 때 수집·요약은 한 번만 하고 알림은 전원에게 가려면, 무엇을 "같은 키워드"로 볼 것인가.
3. 요약 1건을 사용자 x 채널만큼의 알림으로 펼치는 일(fan-out)을 어디서 하는가. 이 위치가 서비스 간 의존 방향과 멱등 키를 결정한다.
4. 채널 주소(Telegram chat id, webhook URL)를 이벤트에 어떻게 실을 것인가.

## 결정

### 소유권

| 개념 | 소유 | 이유 |
| --- | --- | --- |
| 채널 바인딩 — 사용자의 채널별 주소 | user-service | "어디로 받을지"는 사용자 프로필의 일부다. 주소는 암호화해 저장한다 |
| canonical 키워드 — 정규화된 대표값 | user-service | 정규화는 등록 시점에 일어난다. 등록 API가 여기 있다 |
| 구독 = (사용자, 키워드, 채널 목록) | user-service | 사용자·키워드·바인딩이 한 저장소 안에 있어 한 트랜잭션으로 정합성을 지킨다 |
| 뉴스 묶음, 요약 | collector, ai | 지금과 같다 |
| 역산 실행 — 요약(키워드 K) → {(사용자, 채널, 주소 참조)} 로 펼치기 | notification-service의 `routing` | 데이터는 user-service가 조회 API로 주고, routing은 펼치기만 한다 |
| 알림 접수·발송·재시도 | notification-service, notification-worker | 지금과 같다 |
| 발송 이력 read model | history-service (미구현) | 여러 이벤트를 사용자 축으로 모아 조회한다 |

구독을 소유하는 컨텍스트는 user-service 하나다. 별도 subscription 서비스는 두지 않는다. 사용자·키워드·바인딩이 이미 거기 있고, 셋을 묶는 것이 구독이다.

### 키워드 identity

등록된 문자열을 다음 규칙으로 정규화한 값이 키워드의 identity다.

```
normalize(raw) = NFKC → trim → 연속 공백을 하나로 → casefold(Locale.ROOT) → 양끝 구두점 제거
```

정규화 결과가 같으면 같은 키워드다. `tesla`, `Tesla`, ` TESLA `는 하나로 합쳐진다. 이 규칙은 코드로 고정되고 사람 판단이 들어가지 않는다.

언어 간 동의어(`테슬라` ↔ `tesla` ↔ `TSLA`)는 정규화로 합칠 수 없다. 자동 병합은 하지 않는다. "애플"이 과일인지 회사인지를 기계가 정하면 오배송이 사용자에게 바로 간다.
필요해지면 운영자가 관리하는 alias 표를 두고, 그다음에 LLM이 alias를 **제안**하고 사람이 승인하는 순서로 간다. 승인 전 제안은 매칭에 쓰지 않는다.

뒷단(collector, ai)이 쓰는 join key는 정규화된 문자열 `canonicalKey`다. 지금 두 서비스가 이미 문자열로 뉴스를 찾고 요약을 저장하므로 저장 구조가 바뀌지 않는다. 대가는 키워드 이름 변경을 "새 키워드"로 다루게 된다는 것이다. 이름 변경·병합이 실제로 필요해지면 `keywordId` 기반으로 옮긴다. 그때를 위해 활성 키워드 API 응답에는 `keywordId`를 처음부터 함께 싣는다.

### fan-out은 notification-service의 routing이 한다

ai-service는 요약이 생겼다는 사실만 자기 topic에 1건 발행한다. 누가 받는지는 모른다.

```
ai outbox(요약 1행) ──▶ Kafka ai.summary.created x1 (key = keyword)
                              │
                              ▼
               notification-service [routing]
                 RoutingJob(summaryId) unique          ← 같은 이벤트를 두 번 받아도 한 번만 펼친다
                 GET user-service /internal/subscriptions?keyword=K
                   → [(userId, channel, recipientRef)]
                 requestId = "sum:{summaryId}:u:{userId}:c:{channel}"
                 → RequestNotificationUseCase를 프로세스 안에서 사용자 x 채널만큼 호출
                              │  기존 outbox → notification.dispatch
                              ▼
               notification-worker
                 recipientRef → user-service에서 실제 주소 조회 (Redis 캐시)
                 바인딩이 해지됐으면 SUPPRESSED로 끝낸다
```

routing은 notification-service 안의 패키지이지 별도 서비스가 아니다. 다만 자기 consumer group, 자기 컬렉션(`RoutingJob`), 자기 topic 경계를 가진다. 나중에 서비스로 떼어내야 할 때 옮기는 비용이 거의 없도록 하기 위해서다. 떼어내는 시점은 routing의 확장 요구가 notification 접수와 달라질 때다.

routing이 `notification.requested` topic을 거치지 않고 유스케이스를 직접 호출하는 이유는 같은 프로세스 안에서 Kafka를 한 번 더 타는 것이 얻는 것이 없기 때문이다. topic은 외부 producer(user-service 등)를 위해 그대로 둔다.

관리자 알림(`ai.keyword.quarantined`)도 같은 routing을 탄다. 구독 조회 대신 routing 설정의 관리자 수신처를 쓰고 `requestId = "adm:{eventId}:c:{channel}"`이다. 시스템 사용자를 만들어 구독으로 표현하는 방식은 쓰지 않는다. 관리자 수신처가 user-service에 있으면 "user-service 장애를 알리는 알림이 user-service에 의존"하게 된다.

### 홉마다 멱등 키가 있다

| 홉 | 키 | 막는 것 |
| --- | --- | --- |
| 구독 | (userId, canonicalKey) unique | 같은 사용자의 같은 키워드 중복 |
| 요약 | (keyword, newsHash) unique | 같은 뉴스 묶음 재실행 시 같은 summaryId, 이벤트 재발행 없음 |
| ai outbox | eventKey = summaryId | 같은 요약의 outbox 행 중복 (ADR 022) |
| routing | RoutingJob(summaryId) unique | at-least-once 소비의 중복 펼치기 |
| 알림 접수 | requestId = f(summaryId, userId, channel) | 어느 지점에서 죽고 다시 돌아도 같은 requestId (ADR 013) |
| dispatch, vendor | notificationId, idempotency key | ADR 013 그대로 |

requestId가 `(summaryId, userId, channel)`의 순수 함수라는 것이 핵심이다. routing이 1만 명을 펼치다 중간에 죽어도 다시 시작하면 이미 접수된 것은 `duplicated`로 조용히 걸러지고 나머지만 접수된다. 진행 커서는 성능을 위한 것이지 정확성에 필요하지 않다.

### 주소는 이벤트에 싣지 않는다

이벤트와 알림 레코드에는 `recipientRef`(채널 바인딩 id)만 있다. Telegram chat id나 webhook URL은 worker가 전송 직전에 user-service에서 받는다. Kafka, Mongo, 로그 어디에도 주소가 남지 않는다.
notification-contract의 `NotificationRequestedEvent.recipient`는 타입을 바꾸지 않고 의미만 "주소"에서 "주소 참조"로 바꾼다. Telegram의 chat id처럼 비밀이 아닌 값도 같은 규칙을 따른다. 채널마다 규칙이 다르면 worker가 채널별로 분기해야 한다.

Slack·Discord의 개인 수신은 사용자가 자기 incoming webhook URL을 등록하는 모델이다. 봇 앱(OAuth 설치, 사용자 id 조회)은 범위를 크게 키우므로 쓰지 않는다. Telegram은 봇에 `/start <token>`을 보내 chat id를 연결한다.

### topic과 계약

| topic | key | producer | consumer | 필드 |
| --- | --- | --- | --- | --- |
| `ai.summary.created` | keyword | ai-service | notification routing, (history) | `AiSummaryCreatedEvent` — ADR 023 |
| `ai.keyword.quarantined` | keyword | ai-service | notification routing | `AiKeywordQuarantinedEvent` — ADR 023 |
| `notification.requested` | requestId | 외부 producer | notification-service | 기존 (ADR 013). routing은 거치지 않는다 |
| `notification.dispatch` | requestId | notification-service | notification-worker | 기존 |

ai 계약은 `ai-contract` 모듈이다(ADR 023). 계약 모듈은 data class와 enum만 가진다(ADR 012).

## 검토한 대안

- **ai-service가 구독자를 조회해 사용자 x 채널만큼 발행** — ai가 user-service와 알림 채널에 결합된다. 1만 명 fan-out이 `AiOutbox`를 채워 요약 relay가 알림 지연의 볼모가 되고, LLM 실패와 fan-out 실패가 같은 재시도 루프에 섞인다.
- **user-service가 `ai.summary.created`를 소비해 알림 요청을 발행** — 구독 데이터는 거기 있지만, 구독 관리 컨텍스트가 알림 오케스트레이션까지 떠안는다.
- **별도 routing 서비스** — 소유권은 가장 깨끗하지만 배포·모니터링·outbox 한 벌이 늘어난다. 현재 규모에서 과설계다. 패키지 경계로 대신한다.
- **채널당 outbox 1행 (ai)** — ADR 022 반려안. ai가 채널을 아는 것 자체가 문제다.
- **LLM 자동 동의어 병합** — 오병합이 오배송으로 직결된다. 제안까지만 한다.
- **keywordId를 뒷단 join key로** — 이름 변경·병합이 가능하지만 collector·ai의 저장 구조가 바뀐다. 필요가 생길 때 간다.
- **주소를 이벤트에 직접** — 단순하지만 webhook URL이 Kafka와 로그에 남는다.

## 단계

각 단계는 독립 배포·독립 ADR이다.

| 단계 | 내용 | 모듈 |
| --- | --- | --- |
| F′ | ai는 도메인 이벤트만 발행, `ai-contract` 모듈 (ADR 023) | ai-service, ai-contract |
| S1 | 정규화, canonical 키워드, 구독, 채널 바인딩, internal API 3개 | user-service |
| R1 | routing: consumer, RoutingJob, 결정적 requestId, 본문 렌더링, 관리자 수신처 | notification-service, notification-core |
| W1 | worker: 주소 조회·캐시, SUPPRESSED, `sent:{requestId}` 가드 | notification-worker |
| G | 전체 사이클 통합·e2e | e2e-test |
| Q1 | requestId로 알림 조회 API | notification-service |

R1까지가 사용자 알림의 최소 완성이다. alias, LLM 제안, routing 서비스 분리, SMS·Kakao·Email은 보류다.

## 트레이드오프

- 장점: 
  - 요약 파이프라인과 알림 fan-out이 분리되어 한쪽 장애가 다른 쪽을 막지 않는다. 
  - 같은 키워드를 몇 명이 등록해도 수집·요약은 한 번이다. 
  - 어느 홉에서 재시도해도 사용자에게 알림이 두 번 가지 않는다. 
  - 주소가 이벤트·로그에 남지 않는다.

- 단점: 
  - user-service에 aggregate 세 개와 API 세 개가 늘고 암호화 키 관리가 생긴다. 
  - routing이 user-service를 동기 호출하므로 user-service가 죽으면 알림이 밀린다(요약은 계속된다). 
  - 키워드 이름 변경은 새 키워드다. 
  - worker가 전송마다 주소를 조회한다(캐시로 완화).

## 후속

- 발송 이력 read model(history-service). 그전까지는 notification-service의 Notification 컬렉션과 Q1 조회 API로 답한다
- 인기 키워드의 fan-out 배치·backpressure (구독 조회 페이징, dispatch topic 파티션)
- Telegram 봇 차단(403) → 바인딩 BOUNCED 반영
- 운영자 alias 표
