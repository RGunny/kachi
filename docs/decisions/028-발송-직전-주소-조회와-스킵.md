# 028. 발송 직전 주소 조회와 스킵

## 배경

ADR 025는 알림 이벤트와 알림 레코드에 수신자 식별자(`recipientId`, user-service 사용자 id)와 채널만 싣고, 실제 수신 주소(Telegram chat id, Slack·Discord webhook URL)는 notification-worker가 전송 직전에 user-service에서 받기로 했다.
user-service는 그 조회 API(`GET /internal/users/{userId}/channel-bindings/{channel}`)를 열었고(ADR 026), routing은 사용자 id를 `recipientId`로 싣는다(ADR 027).
문자·이메일은 비용과 설정이 무거워 Slack·Discord·Telegram으로 먼저 개발했는데, 이 채널들의 수신처는 chat id나 webhook URL이라 일반 사용자가 발급·관리하기 어렵다(ADR 016). 그래서 설계 중에 worker 설정에 고정해 둔 관리자 수신처가 그대로 굳었다. 관리자 수신처를 따로 보관하고 관리자 알림을 구분하는 안도 검토했지만, 일반적인 발송 파이프라인을 먼저 완성하고 필요해지면 그때 더하기로 했다.

이 ADR을 쓰는 시점의 worker는 아직 그 조회를 하지 않는다. `recipientId`를 그대로 주소로 쓴다. Telegram sender는 사용자 id를 chat id 자리에 넣어 보내고, Slack·Discord sender는 수신자를 무시하고 worker 설정의 전역 webhook 하나로 보낸다(ADR 027 운영 제약).
사용자별 채널 발송이 실제로 동작하려면 이 마지막 구간을 채워야 한다.

정해야 할 것은 다음이다.

1. 주소 조회를 어느 층이 하는가. sender인가, dispatch 유스케이스인가.
2. 바인딩이 없거나 해지된 수신자의 알림을 어떻게 끝내는가.
3. user-service 장애를 발송 실패와 어떻게 구분하는가.
4. 전송마다 조회하는 비용을 어떻게 줄이고, 그 캐시의 경계는 어디까지인가.
5. vendor 호출은 됐는데 결과를 저장하기 전에 worker가 죽었을 때 같은 알림이 다시 나가는 것을 무엇이 막는가.
6. worker의 전역 webhook 설정을 언제 지우는가.

## 검토한 선택지

주소 조회 층에 대해 셋을 봤다.

| 선택 | 장점 | 단점 |
| --- | --- | --- |
| sender 앞의 데코레이터가 조회해 주소를 채운다 | dispatch 유스케이스가 바뀌지 않는다 | `SendNotificationResult`가 성공·실패 4종뿐이라 "보내지 않고 끝낸다"를 표현할 수 없다. 스킵은 aggregate 전이(`SUPPRESSED`)이고 claim fencing CAS를 타야 하는데 sender 층에서는 그 저장 경계에 닿지 못한다 |
| `SendNotificationResult`에 `Suppressed`를 더하고 sender가 조회한다 | 유스케이스는 결과만 보면 된다 | sender의 책임이 "주소를 받아 보낸다"에서 "수신자를 해석하고 보낸다"로 넓어진다. 채널마다 같은 조회 코드가 생긴다 |
| dispatch 유스케이스가 outbound 포트(`RecipientResolverPort`)로 조회한다 | 스킵이 다른 종결(SENT·DEAD)과 같은 finalize 경로를 탄다. sender는 주소만 받는다. 조회 실패를 발송 실패와 같은 재시도 분류로 다룬다 | notification-core의 유스케이스와 command가 바뀌고 worker 조립이 따라 바뀐다 |

세 번째를 택했다. 스킵은 발송의 결과가 아니라 발송 전에 내리는 결정이고, 그 결정의 기록은 aggregate 상태다.

## 결정

### 조회는 `DispatchNotificationService`가 `RecipientResolverPort`로 한다

```kotlin
interface RecipientResolverPort {
    suspend fun resolve(recipientId: String, channel: NotificationChannel): ResolvedRecipient
}
// ResolvedRecipient = AvailableRecipient(address) | UnavailableRecipient(reason)
// RecipientUnavailableReason = NOT_FOUND | PENDING | REVOKED | ADDRESS_MISSING | CHANNEL_MISMATCH
```

발송 순서는 다음과 같다.

```
dedupe SETNX → claim(PROCESSING)
  → resolve(recipientId, channel)
       Unavailable        → SUPPRESSED
       조회 실패(예외)     → RETRY_WAIT | DEAD
  → vendor idempotency key
  → sent 가드 SETNX(notification:sent:{requestId})
       실패              → SUPPRESSED
  → sender.send(address)
  → SENT | RETRY_WAIT | DEAD
```

조회는 claim 뒤, idempotency key 앞이다. claim 전에 조회하면 중복 메시지마다 user-service를 부르고, idempotency key 뒤에 조회하면 스킵될 알림에 vendor 키가 남는다.

sender는 `SendNotificationCommand.address`를 받는다. command에서 `recipientId`는 뺐다. sender가 알아야 하는 것은 "어디로"뿐이고, "누구"까지 들고 있으면 한 command에 수신자 이름이 둘이 된다.  
Slack·Discord 클라이언트는 webhook URL을 생성자가 아니라 `send`마다 받는다. Telegram은 `address`를 chat id로 쓴다.

### 없거나 해지된 바인딩은 스킵(SUPPRESSED), 조회 실패는 RETRY_WAIT

| user-service 응답 | 결과 |
| --- | --- |
| ACTIVE, 주소 있음, 채널 일치 | 발송 |
| PENDING · REVOKED · 404 · 사용자 id가 UUID 형식이 아님 | `SUPPRESSED`, 사유 `recipient unavailable: {reason}` |
| ACTIVE인데 주소 없음 · 응답 채널 불일치 | `SUPPRESSED` (`ADDRESS_MISSING` · `CHANNEL_MISMATCH`, 계약 위반 방어) |
| 5xx · 그 밖의 4xx · 응답 형식 오류 · 연결 실패 | `RecipientResolveException(RECIPIENT_RESOLVE_FAILED)` → 기존 재시도 정책으로 `RETRY_WAIT` 또는 `DEAD` |
| 응답 지연 | `RecipientResolveException(RECIPIENT_RESOLVE_TIMEOUT)` → 같음 |

SUPPRESSED는 `PROCESSING`에서만 가는 종착 상태다(ADR 027에서 추가). vendor를 부르지 않았으므로 `dispatchAttempts`를 올리지 않고, listener는 SENT·DEAD와 같이 ack한다.
조회 실패는 한 번의 시도로 세어 attempts를 올린다. Kafka 재전달 횟수와 맞아야 한다.

실패 코드 `RECIPIENT_RESOLVE_FAILED`·`RECIPIENT_RESOLVE_TIMEOUT`의 source는 `APPLICATION`이다. user-service는 vendor도 broker도 아니며, 기존 `DISPATCH_NOT_READY`·`DISPATCH_PROCESSING_TIMEOUT`이 같은 이유로 그 값을 쓴다.

user-service 호출에 재시도와 서킷 브레이커를 두지 않는다. routing·ai·collector의 user-service 클라이언트와 같고, 재시도는 Kafka 재전달과 `RETRY_WAIT`가 구동한다(ADR 015).

### 캐시는 Redis, TTL 5분, 없음도 캐시한다

worker는 user-service의 저장소를 직접 읽지 않는다. 주소는 user-service의 MySQL에 암호화돼 있고 키는 user-service만 가지며(ADR 026), 다른 서비스의 저장소를 직접 읽지 않는 것은 collector·ai·routing과 같은 규칙이다. 캐시는 worker 자신의 Redis(dedupe·idempotency key와 같은 인스턴스)에 두고, user-service는 이 캐시를 모른다.

```
resolve(recipientId, channel)
  │
  ① worker Redis  GET notification:recipient:{recipientId}:{channel}
  │     hit  ──▶ 캐시된 결과 (user-service 호출 없음)
  │     miss
  ▼
  ② user-service  GET /internal/users/{recipientId}/channel-bindings/{channel}
  │     200 ACTIVE + address  ──▶ AvailableRecipient
  │     200 PENDING·REVOKED / 404 ──▶ UnavailableRecipient
  │     5xx·timeout·연결 실패 ──▶ RecipientResolveException (캐시하지 않음)
  ▼
  ③ worker Redis  SET notification:recipient:{recipientId}:{channel}  TTL 5m
  │     Available·Unavailable 둘 다 저장
  ▼
  결과 반환
```

키 `notification:recipient:{recipientId}:{channel}`, 값은 조회 결과(주소 또는 없는 사유), TTL `kachi.notification.recipient.cache-ttl`(기본 5분).

- 없는 사유(`UnavailableRecipient`)도 캐시한다. 해지된 바인딩으로 오는 알림이 구독자 fan-out으로 몰릴 때 user-service를 반복 부르지 않기 위해서다. 대가는 바인딩이 `PENDING`에서 `ACTIVE`로 바뀐 것이 최대 TTL만큼 늦게 반영되는 것이다.
- Redis 읽기·쓰기 실패는 조회 실패(`RECIPIENT_RESOLVE_FAILED`)로 나간다. 캐시 장애를 조용히 user-service 직접 호출로 우회하면 Redis 장애가 user-service 부하 폭증으로 바뀐다. 기존 dedupe·idempotency 어댑터도 Redis 예외를 삼키지 않는다.
- 무효화는 TTL뿐이다. user-service가 바인딩 변경을 worker에 알리는 이벤트는 두지 않는다.

**주소가 Redis에 TTL 동안 남는다.** ADR 025의 "Kafka, Mongo, 로그 어디에도 주소가 남지 않는다"는 영속·전파 매체를 말한 것이고, Redis 캐시는 발송 직전 worker의 작업 기억이다. 이 경계를 여기 적어 둔다. 코드에서 주소가 저장소나 로그에 닿는 자리에는 `// ADDRESS-EXPOSURE` 마커를 단다. 로그에서 주소를 지우는 일은 이 단계 범위가 아니다.

### `notification:sent:{requestId}` 가드 — 발송 직전 SETNX

막으려는 상황은 하나다. **vendor 호출은 끝났는데 결과를 저장하기 전에 worker가 죽었을 때.** stale PROCESSING 회수가 알림을 `RETRY_WAIT`로 돌리면 다음 claim이 성공해 같은 알림이 한 번 더 나간다.

기존 가드는 이 상황을 막지 못한다.

| 층 | 막는 것 | 이 상황에서 |
| --- | --- | --- |
| 접수 `requestId` unique (ADR 013) | 같은 요청으로 두 번째 `Notification`이 생기는 것 | `Notification`은 하나뿐이라 관여하지 않는다 |
| dispatch dedupe `notification:dispatch:{notificationId}` | 같은 dispatch 메시지의 동시 실행 | `RETRY_WAIT` 저장 시 풀리므로 회수 뒤 재발송을 막지 않는다 |
| vendor idempotency key | vendor가 그 키로 중복을 거르는 것 | Slack·Discord webhook은 키를 받지 않는다 |

가드는 idempotency key 뒤, `sender.send` 직전에 잡는다. 가드와 실제 호출 사이의 창을 최소로 해야 반대 손실 — 가드는 잡았는데 호출 전에 죽어 회수 뒤 `SUPPRESSED`로 유실 — 이 작아진다.
두 손실 중 이중 발송이 유실보다 사용자에게 나쁘다고 판단했다. 알림 하나를 놓치는 것은 다음 요약에서 회복되지만 같은 알림이 두 번 오는 것은 사용자가 바로 본다.

- 키는 core가 조립하고 기존 `NotificationDeduplicationPort`를 그대로 쓴다. 새 포트·어댑터는 없다.
- TTL은 vendor idempotency key와 같은 24시간이다.
- 가드 실패는 `SUPPRESSED`, 사유 `already sent`다.
- `RETRY_WAIT`로 확정한 뒤, 그리고 `send` 도중 예상 밖 예외로 빠져나갈 때 푼다. `SENT`·`DEAD`·`SUPPRESSED`와 stale finalize에서는 풀지 않는다.

이 가드는 접수 `requestId` unique와 역할이 다르다. 접수는 "같은 요청으로 두 번째 `Notification`을 만들지 않는다", 이 가드는 "같은 `Notification`을 두 번 보내지 않는다". 네 층의 관계는 `docs/알림-멱등-가드.md`에 있다.

### worker 전역 webhook 설정을 지운다

`kachi.notification.sender.slack.webhook-url`·`discord.webhook-url`과 그 blank 검증을 지운다. 주소가 발송마다 들어오므로 sender가 주소를 갖지 않는다. Telegram의 `bot-token`은 봇 자격이지 수신처가 아니라 그대로다.

local seed의 관리자 채널 바인딩은 `kachi.user.seed.admin-addresses.*`로 실주소를 받는다. 비어 있으면 형식만 맞는 placeholder를 쓰고, 이미 있는 바인딩의 주소가 설정값과 다르면 갱신한다. 로컬에서 실 webhook으로 격리 알림을 받는 경로는 이제 이것뿐이다.

### 설정

```yaml
kachi:
  notification:
    recipient:
      cache-ttl: 5m
      user-service:
        base-url: ${KACHI_USER_SERVICE_BASE_URL:}
        channel-binding-path: /api/v1/internal/users/{userId}/channel-bindings/{channel}
        timeout: 3s
        max-in-memory-size: 262144
```

`base-url`이 비어 있으면 기동 시 실패시킨다(routing과 같은 규칙).

### 지표

- dispatch 결과 `suppressed`가 `sent`·`retry_wait`·`dead` 옆에 선다.
- `kachi.notification.recipient.resolve` 카운터, tag `channel`·`result(available|unavailable|failed)`·`source(cache|user_service)`. 수신자 id와 주소는 tag에 넣지 않는다.

## 검토한 대안

- **sender 데코레이터 / `SendNotificationResult.Suppressed`**
  - 위 "검토한 선택지". 스킵을 sender 결과로 표현하면 aggregate 전이와 저장 경계에 닿지 못한다.
- **관리자 수신처를 worker 설정에서 해석**
  - 처음 이렇게 설계했다. `recipientId == admin`이면 설정의 채널별 주소를 쓰는 분기였다. 발송 경로가 수신자의 역할을 알게 되고, 관리자 주소가 user-service 바인딩과 worker 설정 두 곳에 생긴다. W0에서 격리 알림 수신자를 user-service 관리자로 옮겼으므로(ADR 025·027) worker에는 분기가 없다.
- **`sent:{requestId}` 가드 생략**
  - "접수 requestId unique와 dispatch dedupe·claim CAS가 있어 지키는 불변식이 없다"는 이유로 한 번 뺐었다. 회수 뒤 재발송 시나리오를 다시 보니 그 셋이 모두 비켜 간다. 발송 모듈의 중복 방어는 층마다 다른 상황을 막으므로 "다른 층이 있으니 불필요"로 빼지 않는다.
- **가드를 claim 직후에**
  - 조회·idempotency key까지의 시간이 창에 들어가 유실 쪽 손실이 커진다.
- **Redis 장애 시 user-service로 우회**
  - 캐시 장애가 origin 부하로 전이된다.
- **없는 사유는 캐시하지 않음**
  - 해지된 바인딩 하나에 fan-out이 몰리면 user-service를 그 수만큼 부른다.
- **로그·failure message에서 주소 제거를 이번에**
  - 로컬 개발 단계라 마커만 남기고 뒤로 미룬다.
- **user-service 호출에 재시도·서킷 브레이커**
  - ADR 015·027과 같은 이유로 두지 않는다.

## 트레이드오프

- 장점:
  - 사용자가 등록한 채널 주소로 알림이 간다. ADR 025의 흐름이 끝까지 이어진다.
  - 주소는 user-service 저장소와 worker의 발송 직전, 그리고 TTL 캐시에만 있다. 이벤트·알림 레코드·job에는 없다.
  - 해지된 바인딩의 알림은 vendor를 부르지 않고 `SUPPRESSED`로 남아 조회할 수 있다.
  - 회수 뒤 재발송이 가드에 걸려 같은 알림이 두 번 가지 않는다.
  - worker에 관리자 분기·전역 webhook이 없다. sender는 주소를 받아 보내기만 한다.
- 단점:
  - user-service가 죽으면 발송이 `RETRY_WAIT`로 밀린다. 재시도 한도를 넘으면 `DEAD`다.
  - 바인딩 변경이 최대 5분 늦게 반영된다.
  - 주소가 Redis에 TTL 동안 남는다.
  - 가드를 잡고 호출 전에 죽으면 그 알림은 `SUPPRESSED`로 유실된다. 창은 한 번의 `send` 호출 준비 시간이다.
  - Redis 장애가 발송 전체를 세운다(이미 dedupe·idempotency key가 그렇다).

## 운영 제약

- `KACHI_USER_SERVICE_BASE_URL`이 worker에도 필요하다. 비어 있으면 뜨지 않는다.
- `KACHI_NOTIFICATION_SLACK_WEBHOOK_URL`·`KACHI_NOTIFICATION_DISCORD_WEBHOOK_URL`은 더 이상 읽지 않는다. 로컬에서 실 webhook으로 받으려면 `KACHI_USER_SEED_ADMIN_{SLACK_WEBHOOK_URL,DISCORD_WEBHOOK_URL,TELEGRAM_CHAT_ID}`로 seed 관리자 바인딩에 넣는다.
- `SUPPRESSED`는 종착 상태라 자동으로 다시 보내지 않는다. 바인딩을 되살린 뒤 알림을 다시 받으려면 새 요청이어야 한다.
- 가드 키를 수동으로 지우면 그 알림이 다시 나갈 수 있다. 재발송이 목적일 때만 지운다.

## 후속

- Telegram 403(봇 차단) → 바인딩 `BOUNCED` 반영 (ADR 025)
- 바인딩 변경 이벤트로 캐시 무효화 — TTL로 부족해질 때
- 로그·failure message에서 주소 제거 — `// ADDRESS-EXPOSURE` 마커 자리
- internal API 공유 토큰 (ADR 026 착수 조건)
