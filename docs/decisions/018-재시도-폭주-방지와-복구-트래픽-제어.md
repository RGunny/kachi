# 018. 재시도 정책 설계 (재시도 폭주 방지와 복구 트래픽 제어)

## 배경

Kachi는 외부 API와 메시징 기반 비동기 처리를 많이 사용한다.

예:

- collector-service: Google RSS, Naver, Finnhub 같은 뉴스/시장 데이터 provider
- ai-service: LLM provider
- notification-service: Kafka publish, outbox recovery
- notification-worker: Slack, Discord, Telegram 같은 vendor sender

이 외부 시스템은 일시/장기 장애, rate limit, timeout 등 우리가 알 수 없는 장애를 낼 수 있다.
장애가 발생하면 재시도는 복구 수단이지만, 잘못 설계하면 장애를 증폭시키는 도구가 된다.

가장 위험한 상황은 다음과 같다.

```text
외부 시스템 장애
  -> 요청 실패
  -> 내부 retry/backoff 대기열 증가
  -> 외부 시스템 복구
  -> 누적된 retry가 동시에 재개
  -> 외부 시스템 또는 우리 서비스가 다시 과부하
  -> 더 많은 timeout/retry 발생
```

backoff와 jitter는 재시도 시점을 흩을 수 있지만, 재시도 총량 자체를 줄이지는 못한다.
따라서 안정성은 재시도 횟수를 늘리는 것이 아니라, 언제 재시도를 멈추고 언제 천천히 복귀할지를 결정하는 설계에서 나온다.

## 결정

Kachi의 재시도 정책은 다음 순서의 방어선을 기본 원칙으로 둔다.

```text
1. retryable / non-retryable 실패 분류
2. bounded retry attempts
3. exponential backoff + jitter
4. retry budget
5. circuit breaker
6. half-open probe 제한
7. slow start 복귀
8. bulkhead / rate limit
9. DEAD / DLT / 운영자 복구 큐
```

이 문서는 즉시 모든 모듈에 구현한다는 뜻이 아니라, 앞으로 collector, ai, notification의 외부 I/O와 retry runtime을 확장할 때 따라야 할 공통 설계 기준이다.

## 원칙

### 1. 모든 실패를 재시도하지 않는다

재시도는 실패 분류 이후에만 허용한다.

재시도 대상:

- network timeout
- connection reset
- 일시적 5xx
- provider가 명시한 rate limit
- broker 일시 장애
- 저장소 timeout, network error, primary election처럼 성공 여부가 불확실한 인프라 장애

재시도 비대상:

- 잘못된 request shape
- 인증/권한 오류
- 존재하지 않는 recipient/chat/channel
- schema mismatch
- 같은 payload를 다시 보내도 성공 가능성이 낮은 validation 오류
- CAS 조건 불일치처럼 같은 조건으로 다시 시도해도 성공하지 않는 정상 경쟁 패배

notification의 `RetryFailure`, `RetryPolicy`, `DispatchFailureClassification`은 이 원칙의 초기 구현이다.

### 2. 재시도는 반드시 bounded여야 한다

무한 자동 재시도는 금지한다.

자동 재시도는 정해진 한도에 도달하면 `DEAD`, DLT, 또는 운영자 확인 큐로 이동해야 한다.
운영자가 원인을 확인하고 수동 복구할 수는 있지만, 시스템이 같은 실패를 무기한 자동 반복해서는 안 된다.

notification outbox는 `NotificationOutbox.DEAD`, dispatch는 `Notification.DEAD`로 자동 재시도 종료를 표현한다.

### 3. backoff와 jitter는 필요하지만 충분하지 않다

exponential backoff는 장애 중 요청 압력을 낮추고, jitter는 여러 인스턴스가 같은 시각에 재시도하는 현상을 줄인다.
하지만 둘 다 재시도 총량을 줄이지는 못한다.

따라서 backoff/jitter는 기본값일 뿐, retry budget과 circuit breaker 없이 단독 방어선으로 취급하지 않는다.

초기 구현 기준:

```text
delay = min(baseDelay * multiplier^(attempt - 1), maxDelay)
jitter = random(-jitterRatio, +jitterRatio)
```

rate limit 응답이 `Retry-After`를 제공하면 provider가 준 값을 우선하되, 내부 max delay와 retry budget을 넘지 않는다.
또한 `Retry-After`를 그대로 절대 시각처럼 믿지 않는다.
여러 client가 같은 `Retry-After` 값으로 동시에 복귀하면 다시 피크가 생길 수 있으므로, provider 지시값을 존중하되 jitter를 더해 재시도 시점을 흩는다.

### 4. retry budget으로 재시도 총량을 제한한다

retry budget은 전체 요청 중 재시도가 차지할 수 있는 비율 또는 절대량에 상한을 둔다.
budget은 서비스 전체 단위보다 dependency 단위로 우선 잡는다.
Slack 장애가 Telegram, MongoDB, Redis, Kafka 같은 다른 dependency의 처리량까지 잠식하면 안 되기 때문이다.

예:

```text
최근 1분 성공/신규 요청 1000건
retry budget 10%
허용 retry 100건
```

budget을 초과한 retry는 즉시 재시도하지 않는다.
상황에 따라 다음 중 하나로 처리한다.

- 더 긴 delay로 밀어낸다.
- `RETRY_WAIT`에 남겨 다음 scheduler tick으로 넘긴다.
- 자동 재시도 한도에 가까운 경우 `DEAD` 또는 운영 큐로 보낸다.

retry budget은 특히 다음 상황에서 중요하다.

- 외부 provider 장기 장애 후 복구
- Kafka retry topic 또는 outbox에 대량 메시지가 쌓인 경우
- 다수 인스턴스가 동시에 같은 provider로 재시도하는 경우

예:

```text
notification-worker 전체 retry budget
  ├─ Slack retry budget
  ├─ Discord retry budget
  └─ Telegram retry budget

collector-service 전체 retry budget
  ├─ Google RSS retry budget
  ├─ Naver retry budget
  └─ Finnhub retry budget
```

### 5. circuit breaker는 차단뿐 아니라 복귀 정책까지 포함한다

circuit breaker는 연속 실패율이나 slow call 비율이 임계치를 넘으면 외부 호출을 차단하고 빠르게 실패시킨다.
그러나 차단만으로는 충분하지 않다.

문제는 `OPEN -> HALF_OPEN -> CLOSED` 복귀 순간이다.
OPEN 동안 쌓인 요청이 CLOSED 전환과 동시에 몰리면, 막 복구된 외부 시스템이나 우리 서비스가 다시 과부하될 수 있다.

따라서 circuit breaker 설정은 다음을 함께 가져야 한다.

- failure rate threshold
- slow call duration threshold
- slow call rate threshold
- wait duration in open state
- permitted calls in half-open state
- half-open probe timeout
- closed 전환 이후 slow start 또는 rate limit

Resilience4j 기준 예시:

```kotlin
CircuitBreakerConfig.custom()
    .failureRateThreshold(50.0f)
    .slowCallDurationThreshold(Duration.ofSeconds(3))
    .slowCallRateThreshold(80.0f)
    .waitDurationInOpenState(Duration.ofSeconds(60))
    .permittedNumberOfCallsInHalfOpenState(10)
    .build()
```

이 설정은 개념 예시다.
실제 값은 provider의 SLA, timeout, rate limit, 요청량, 비용을 기준으로 모듈별로 잡는다.

`slowCallDurationThreshold`와 `slowCallRateThreshold`는 느린 호출을 실패 신호로 판단해 circuit breaker를 다시 OPEN으로 돌리는 기준이다.
이 설정만으로 HALF_OPEN 이후 트래픽을 점진적으로 늘리는 slow start가 자동 구현되지는 않는다.
slow start는 rate limiter, token bucket, scheduler batch size, Kafka consumer pause/resume, worker concurrency 같은 별도 트래픽 제어 장치와 함께 구현해야 한다.

### 6. half-open은 probe이지 정상 트래픽 복귀가 아니다

HALF_OPEN 상태의 요청은 정상 트래픽이 아니라 복구 확인용 probe다.
probe 수는 작아야 하며, probe 성공이 곧바로 전체 트래픽 허용을 의미해서는 안 된다.

여러 서비스가 같은 외부 시스템을 호출하는 MSA에서는 각 서비스의 circuit breaker가 독립적으로 half-open probe를 보낸다.
서비스 수가 늘수록 모든 호출자의 probe가 동시에 몰릴 수 있다.

따라서 provider별로 가능한 경우 다음 중 하나를 둔다.

- 서비스별 provider 호출 rate limit
- 공통 Redis token bucket
- provider gateway 또는 shared client runtime
- scheduler shard / partition 단위 분산
- half-open probe jitter

### 7. closed 복귀는 slow start로 처리한다

HALF_OPEN probe가 성공해 CLOSED로 돌아가도, 즉시 전체 대기 트래픽을 풀지 않는다.

slow start 예:

```text
0초: 정상 처리량의 10% 허용
30초: 30% 허용
60초: 60% 허용
90초: 100% 허용
```

slow start 중 slow call 비율이나 실패율이 다시 높아지면 circuit breaker를 다시 OPEN으로 전환한다.

이 원칙은 외부 시스템 보호뿐 아니라 우리 서비스 보호에도 필요하다.
쌓인 retry를 한 번에 처리하면 외부 API가 아니라 우리 worker, DB, Redis, Kafka consumer가 먼저 병목이 될 수 있다.

따라서 queue 기반 재시도에는 backlog drain policy가 필요하다.
Kafka retry topic, outbox, scheduler queue에 쌓인 작업은 circuit breaker가 CLOSED로 돌아온 뒤에도 정해진 속도로만 소진한다.

drain policy는 다음 값을 가진다.

- 단위 시간당 처리량
- provider별 처리량
- consumer concurrency
- scheduler batch size
- 오래된 retry의 DEAD/DLT 전환 기준
- backlog size/age 알림 기준

### 8. bulkhead로 장애 전파를 막는다

외부 시스템별 호출 동시성은 분리한다.

예:

- Slack sender bulkhead
- Discord sender bulkhead
- Telegram sender bulkhead
- Naver provider bulkhead
- LLM provider bulkhead

한 provider의 장애가 전체 worker thread, event loop, connection pool, Redis, MongoDB를 잠식하지 않게 한다.

bulkhead는 다음 단위 중 하나로 둔다.

- 동시 실행 수
- connection pool
- queue size
- per-provider scheduler concurrency
- Kafka partition 또는 consumer concurrency

bulkhead queue가 가득 차면 무기한 대기하지 않고 빠르게 실패하거나 `RETRY_WAIT`/운영 큐로 넘긴다.

retry가 있는 외부 side effect는 idempotency 전략과 함께 설계한다.
Slack/Discord webhook처럼 강한 idempotency를 제공하지 않는 dependency는 재시도 횟수, visibility timeout, recovery 정책을 더 보수적으로 잡는다.
idempotency가 약한 dependency에서 공격적으로 재시도하면 장애 복구보다 중복 side effect 위험이 더 커질 수 있다.

### 9. DLT와 DEAD는 실패가 아니라 자동화의 경계다

DLT와 DEAD는 시스템이 실패했다는 뜻만이 아니다.
자동화가 더 진행하면 위험하므로 멈춘다는 경계다.

운영자는 DEAD/DLT를 보고 다음을 판단한다.

- 외부 장애가 끝났는지
- payload 또는 credential 문제가 있는지
- 수동 복구할지
- 폐기할지
- 더 긴 delay로 다시 넣을지

즉, 안정성은 자동 재시도를 많이 하는 데서 나오지 않고, 자동 재시도를 멈추고 사람이 판단할 수 있는 지점을 만드는 데서 나온다.

## Kachi 적용 기준

### notification outbox

목적:

- `Notification + Outbox` 저장 이후 Kafka publish 유실을 복구한다.

현재:

- bounded attempts
- exponential backoff
- `NotificationOutbox.DEAD`
- stale `PUBLISHING` recovery
- admin recover API

후속:

- jitter 추가
- outbox publish retry budget
- Kafka broker 장애 시 publisher circuit breaker 또는 scheduler rate limit
- outbox backlog drain policy
- backlog size/age metric과 alert

### notification dispatch

목적:

- worker가 vendor sender 호출 실패를 재시도한다.

현재:

- retryable / non-retryable 실패 분류
- bounded attempts
- Kafka retry / DLT 연결
- `Notification.RETRY_WAIT` / `Notification.DEAD`
- stale `PROCESSING` recovery

후속:

- sender별 circuit breaker
- sender별 bulkhead
- sender별 retry budget
- sender별 rate limiter
- jitter
- HALF_OPEN 이후 slow start
- retry topic backlog drain policy
- circuit breaker 상태와 retry budget metric
- dispatch DEAD/DLT 운영 API

### collector provider

목적:

- 외부 뉴스/시장 데이터 provider 장애나 rate limit에 대응한다.

현재:

- provider별 WebClient timeout 중심
- retry/circuit breaker/rate limit은 후속으로 남아 있다.

후속:

- provider별 실패 분류
- provider별 retry budget
- provider별 circuit breaker
- provider별 scheduler rate limit
- rate limit 응답 기반 next poll 조정

### ai provider

목적:

- LLM provider timeout, rate limit, 비용 폭주에 대응한다.

후속:

- token/cost budget
- retry budget
- provider circuit breaker
- idempotency 기반 중복 비용 방지
- fallback model 또는 degraded mode

## 구현 지침

새로운 외부 I/O를 추가할 때는 다음 질문에 답해야 한다.

1. 어떤 실패가 retryable인가?
2. 어떤 실패는 즉시 give up 해야 하는가?
3. 최대 자동 재시도 횟수는 몇 번인가?
4. backoff, multiplier, max delay, jitter는 얼마인가?
5. provider가 `Retry-After`를 주면 어떻게 반영하는가?
6. retry budget은 어떤 단위로 잡는가?
7. circuit breaker threshold는 무엇인가?
8. HALF_OPEN probe 수와 timeout은 얼마인가?
9. CLOSED 복귀 후 slow start가 필요한가?
10. bulkhead 동시성/queue 한도는 얼마인가?
11. 자동 재시도 종료 후 DEAD/DLT를 어디에서 조회하고 복구하는가?
12. retry가 몰렸을 때 우리 DB, Redis, Kafka, worker를 어떻게 보호하는가?
13. backlog를 어떤 속도로 소진할 것인가?
14. circuit breaker 상태, retry budget, backlog age/size를 어떻게 관측할 것인가?
15. 외부 side effect의 idempotency 보장은 어느 수준인가?

이 질문에 답하지 못한 외부 I/O는 retry를 단순히 추가하지 않는다.

## 트레이드오프

### 장점

- 장애 중 재시도가 내부/외부 시스템을 동시에 압박하는 상황을 줄인다.
- provider 복구 직후 retry storm을 완화한다.
- 재시도 한도와 운영 큐를 통해 장애 분석 지점을 만든다.
- MSA 환경에서 각 호출자의 독립 circuit breaker가 만드는 복귀 피크를 설계 대상으로 명시한다.

### 단점

- 단순 retry보다 구현과 설정이 복잡하다.
- retry budget, circuit breaker, slow start, bulkhead는 모듈별 트래픽 특성을 알아야 적절한 값을 잡을 수 있다.
- 너무 보수적인 설정은 복구 지연을 늘릴 수 있다.
- DEAD/DLT 운영 도구와 알림이 없으면 자동화가 멈춘 뒤 사람이 놓칠 수 있다.

## 후속 작업

1. `RetryPolicy`에 jitter 설정을 추가한다.
2. notification sender별 circuit breaker, bulkhead, rate limiter 설계를 추가한다.
3. notification dispatch retry budget과 backlog drain policy를 정의한다.
4. circuit breaker 상태, retry budget, backlog age/size metric을 정의한다.
5. dispatch DEAD/DLT 운영 API를 구현한다.
6. collector provider별 retry/circuit breaker/rate limit 정책을 별도 ADR로 구체화한다.
7. ai provider별 token/cost budget과 retry budget을 별도 ADR로 구체화한다.
8. README 또는 운영 문서에 DEAD/DLT 확인과 수동 복구 절차를 추가한다.
