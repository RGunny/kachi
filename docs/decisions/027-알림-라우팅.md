# 027. 알림 라우팅 서비스

`ai.*` 소비와 `notification.requested` 발행 계약은 `RoutingKafkaContractIntegrationTest`가, 전체 사이클은 `e2e-test`가 검증한다(ADR 029).

## 배경

ADR 025는 "요약을 그 키워드 구독자가 정한 채널로 보내는 일", 즉 라우팅을 notification-service 안의 패키지가 맡고
접수 유스케이스(`RequestNotificationUseCase`)를 같은 프로세스 안에서 직접 호출하기로 했다.
ai-service는 요약과 격리를 자기 topic에 발행하고(ADR 023), user-service는 구독과 채널 바인딩을 internal API로 내준다(ADR 026).

그 결정대로 core의 유스케이스·`RoutingJob`과 service의 listener·클라이언트·저장소까지 만들고 나서 생각이 바뀌었다.
만들어 보니 걸리는 것은 책임 분리보다 **부하 격리**였다.

notification-service는 HTTP 접수 API, `notification.requested` listener, outbox publisher를 한 JVM에서 돌린다.
routing이 여기 들어가면 인기 키워드 하나의 요약이 구독자 수만큼 접수를 순차 호출하는 동안
같은 connection pool·consumer 스레드·CPU를 점유한다. 접수 API와 dispatch 발행이 fan-out 하나에 같이 느려진다.
발송을 notification-worker로 분리한 이유가 정확히 이것이었다. 접수와 fan-out을 한 프로세스에 두면 그때 분리했던 것을 다시 붙이는 셈이다.

또 routing이 접수 유스케이스를 직접 호출하면 notification-service의 역할이 "완성된 알림 요청을 신뢰성 있게 접수·발송한다"에서 "요약을 받아 누구에게 보낼지까지 정한다"로 넓어진다. 
user-service 클라이언트, ai 계약 의존, routing 설정이 접수 서비스에 들어온다.

정해야 할 것은 다음이다.

1. routing을 어디에 두는가. 패키지·모듈·프로세스 중 어느 단위인가.
2. routing과 notification-service를 어떻게 잇는가. 직접 호출인가 `notification.requested` 계약인가.
3. 같은 이벤트를 두 번 받아도 한 번만 라우팅하고, 라우팅 도중 죽어도 이어서 할 수 있는 단위(`RoutingJob`)의 모양.
4. 실패했을 때 무엇으로 재시도하는가. routing에 outbox가 필요한가.
5. 사람이 읽을 본문을 누가 만드는가.
6. 알림이 어느 요약·사용자에서 왔는지 `Notification`에 남기는 방식.

## 검토한 선택지

| 선택 | 장점 | 단점 |
| --- | --- | --- |
| notification-service 안의 패키지, 직접 호출 (ADR 025 원안) | 구현·운영이 가장 단순하다. 접수 결과(accepted/duplicated)를 job에 바로 기록한다 | 접수 서비스와 fan-out이 자원·장애·배포·autoscaling 기준을 공유한다. 접수 서비스가 ai 계약과 user-service를 알게 된다 |
| 별도 Gradle 모듈, 같은 프로세스, `notification.requested` 계약 | 코드 경계가 선명하고 나중에 프로세스만 떼면 된다 | Kafka hop 비용은 내면서 런타임 격리는 얻지 못한다. 배포 단위가 같아 "나중에"가 오지 않기 쉽다 |
| 별도 모듈 + 별도 프로세스, `notification.requested` 계약 | 부하·장애·배포가 분리된다. 접수 서비스가 다시 단순해진다. topic이 fan-out의 backpressure가 된다 | 실행 프로세스가 하나 늘고 요약 1건당 Kafka 메시지가 구독자 수만큼 늘어난다. job이 접수·중복 결과를 모른다 |

두 번째 안은 첫 번째와 세 번째의 비용을 둘 다 내는 절충이라 뺐다.
첫 번째 안을 버린 이유는 위의 부하 격리다. worker를 따로 띄우는 구조가 이미 있어 프로세스 하나 더 띄우는 비용은 작고,
`notification.requested`의 소비자·DLT·requestId 멱등이 전부 갖춰져 있어 계약으로 잇는 비용도 거의 없다.

## 결정

### notification-routing은 독립 모듈이자 독립 프로세스다

`notification-routing` Gradle 모듈을 두고 Spring Boot 애플리케이션으로 따로 띄운다(port 8086).
notification-core에 의존하지 않는다. core는 service와 worker가 공유하는 `Notification` 모델이고, routing은 `Notification`을 만들지 않는다.
routing의 도메인은 `RoutingJob` 하나이며 자기 모듈 안에 둔다.

의존은 `ai-contract`(입력 계약)와 `notification-contract`(출력 계약) 두 계약 모듈뿐이다.
채널 타입은 core의 enum 대신 `notification-contract`의 `NotificationChannel`을 그대로 쓴다.
routing의 산출물이 그 계약이고, 중간에 다른 enum을 두면 변환만 늘기 때문이다.

패키지는 다른 서비스와 같은 골격이다.

```
me.rgunny.kachi.notification.routing
├── domain              RoutingJob
├── application         유스케이스, port(persistence·subscriber·messaging), RoutingPolicy, RoutingRequestId
├── adapter/inbound     ai.* Kafka listener, 계약 매퍼, 본문 렌더러
├── adapter/outbound    notification.requested publisher, user-service 클라이언트, Mongo, metrics
└── config
```

자기 consumer group(`notification-routing`), 자기 데이터베이스(`kachi_notification_routing`, 컬렉션 `routing_jobs`), 자기 DLT topic(`notification.routing.dlt`)을 가진다.
Redis는 쓰지 않는다.

### notification-service와는 `notification.requested` 계약으로만 잇는다

routing은 대상마다 `NotificationRequestedEvent`를 `notification.requested`에 발행한다(key = requestId). 접수 유스케이스를 직접 호출하지 않는다.
routing 내부 모델과 계약 모두 수신자를 `recipientId`(사용자 id)와 `channel`로 가리킨다. 주소는 싣지 않는다(ADR 025).
notification-service는 이 topic의 기존 listener로 받아 접수하며 routing의 존재를 모른다.

이 hop이 주는 것은 분리만이 아니다. 구독자 1만 명의 요약은 topic에 1만 건으로 쌓이고 notification-service는 자기 속도로 소비한다.
fan-out이 접수를 밀어붙이지 못하며, ADR 025 후속으로 남겼던 backpressure가 구조로 해결된다.

### `RoutingJob` — 이벤트 1건에 job 1행, eventKey unique

```
RoutingJob(eventKey unique, kind: SUMMARY | QUARANTINE, keyword, status: STARTED → COMPLETED,
           targetCount, publishedCount, createdAt, completedAt)
```

eventKey는 요약이면 `summaryId`, 격리면 `"{quarantineId}:{quarantinedAt epoch millis}"`다. 후자는 ai outbox의 eventKey와 같은 형식이다.
quarantineId만 쓰면 같은 키워드가 나중에 다시 격리됐을 때(같은 id, 다른 시각) 알림이 걸러진다.

소비 흐름은 이렇다.

```
listener ─ 계약 역직렬화(schemaVersion 검사) ─ 본문 렌더링 ─▶ RouteNotificationService
   ① eventKey로 job 조회
        COMPLETED  → 라우팅하지 않는다 (SKIPPED)
        없음       → STARTED로 insert (unique 충돌이면 재조회)
        STARTED    → 다시 발행한다
   ② 대상 목록
        SUMMARY    → user-service GET /internal/subscriptions?keyword=  → [(recipientId, channel)]
        QUARANTINE → user-service GET /internal/users?role=ADMIN         → [(recipientId, channels)] 를 채널로 펼친다
   ③ 대상마다 notification.requested 발행, broker ack까지 순차 대기
   ④ job COMPLETED (publishedCount = 발행 건수)
```

`requestId`는 순수 함수다.

| 대상 | requestId |
| --- | --- |
| 요약 | `sum:{summaryId}:u:{recipientId}:c:{CHANNEL}` |
| 격리 | `qrt:{eventKey}:u:{recipientId}:c:{CHANNEL}` |

③이 중간에 죽으면 job은 STARTED로 남고, 같은 레코드가 다시 오면 ①에서 STARTED를 보고 전체를 다시 발행한다.
이미 발행됐던 대상은 notification-service의 `requestId` 멱등(ADR 013)이 거른다. 진행 커서는 두지 않는다.
정확성에 필요하지 않고, 대상 수가 커져 필요해지면 그때 페이징과 함께 넣는다.

job은 접수 결과를 모른다. 원안의 `acceptedCount / duplicatedCount`는 접수 유스케이스의 반환값에서 왔는데, 계약으로 이으면 그 값이 없다.
"이 요약이 몇 명에게 접수됐는가"는 `GET /api/v1/notifications?requestId=`(Q1)와 사용자·요약 축의 read model(ADR 025의 history-service) 몫이다.

대상이 0건이면 발행 없이 COMPLETED다. 구독자가 없는 키워드의 요약은 정상이고, 관리자가 없거나 관리자에게 바인딩이 없는 것도 정상이다.

### routing에 outbox는 없다. 재시도는 Kafka error handler가 한다

routing이 발행하는 원천은 DB 상태 변경이 아니라 Kafka 레코드다. 발행 도중 죽으면 그 레코드가 재전달되고, `RoutingJob`이 STARTED라 다시 발행하며,
뒷단 notification-service의 `requestId` 멱등(ADR 013)이 중복 접수를 거른다. 이 세 가지로 at-least-once가 닫히므로 outbox(ADR 015)를 한 벌 더 두지 않는다.
대신 발행은 대상마다 broker ack를 기다린다. ack 없이 일괄 전송하면 broker에 닿지 않은 대상까지 COMPLETED로 기록될 수 있다.

`RouteNotificationService`는 예외를 잡지 않는다. user-service 호출 실패, Mongo 장애, 발행 실패는 listener 밖으로 나가고,
`DefaultErrorHandler`가 같은 레코드를 `FixedBackOff(1s, 최대 3회)`로 재전달한 뒤 `notification.routing.dlt`로 보낸다.
routing 안에 재시도 루프를 두지 않는다.

payload를 읽을 수 없거나 `schemaVersion`이 다르면 같은 레코드를 다시 받아도 결과가 같으므로 재시도하지 않고 바로 DLT로 보낸다.

user-service 호출에는 재시도도 서킷 브레이커도 두지 않는다. ai·collector의 user-service 클라이언트와 같다.
user-service가 죽으면 routing이 밀리고 요약은 계속된다(ADR 025 트레이드오프).

### 본문은 routing의 inbound 어댑터가 만든다

`ai-contract`의 이벤트를 사람이 읽을 텍스트로 옮기는 렌더러는 listener 옆에 둔다.
계약 타입에 의존하므로 application 계층에 둘 수 없고, 채널별 포맷은 없다(공통 텍스트 하나).

```
요약:  [{keyword}] {title}

       {content}

       감성 {sentiment} · 기사 {sourceNewsCount}건 · {createdAt}
격리:  [키워드 격리] '{keyword}' — {targetType}, 연속 실패 {n}회, 사유 {reason}, {quarantinedAt}
```

2000자를 넘으면 잘라내고 경고 로그를 남긴다. Discord의 한도가 가장 작다.

keyword는 이벤트의 값, 즉 정규화된 canonicalKey를 그대로 쓴다. ADR 026은 본문에 `displayName`을 쓰기로 했지만 구독 조회 응답에 그 값이 없다.
user-service 응답을 넓히는 것은 user-service의 변경이라 이 단계 밖이다(후속).

### 출처는 계약에 싣고 `Notification`에 남긴다

`NotificationRequestedEvent`에 선택 필드 `origin(summaryId?, keyword?, userId?)`을 더한다. 값을 채우는 producer는 routing뿐이며 다른 producer는 생략한다.
필드 추가는 하위 호환이라 `schemaVersion`은 1을 유지한다. 원안은 계약을 바꾸지 않기로 했지만 계약으로 잇는 이상 출처를 실을 곳이 계약밖에 없다.

notification-service는 이 값을 `Notification`의 값 객체 `NotificationOrigin(summaryId?, keyword?, userId?)`에 옮긴다.
요약 알림은 셋 다, 격리 알림은 keyword와 userId, 출처 없이 들어온 알림은 전부 null이다.
이 필드는 발송 이력을 사용자·요약 축으로 조회하는 read model의 원천이다. 지금은 저장만 한다.

worker의 `save()`는 문서 전체를 다시 쓰므로 worker의 저장 모델도 같은 필드를 알아야 한다. 그래서 notification-worker의 저장 모델·매퍼 두 파일을 함께 바꾼다.

`NotificationStatus`에 `SUPPRESSED`(PROCESSING에서만, terminal)를 더한다. 수신처 바인딩이 해지된 알림을 끝내는 상태이며 쓰는 쪽은 worker(W1)다.

### 키워드 격리 알림

`ai.keyword.quarantined`의 수신자는 user-service의 ADMIN 사용자다. routing이 `GET /internal/users?role=ADMIN`으로 관리자와 그 ACTIVE 바인딩 채널을 받아 관리자 x 채널로 펼치고, 그 뒤의 발행 경로는 요약 알림과 같다.
job 종류는 "누구에게"가 아니라 "어떤 이벤트"이므로 `QUARANTINE`이다. 관리자 주소는 다른 사용자와 같이 채널 바인딩에 있고, 발송 경로는 수신자의 역할을 모른다(ADR 025).
ADMIN 사용자를 만드는 경로는 아직 없다. local은 seed가 관리자 한 명과 세 채널 바인딩을 심고, 그 밖의 환경은 DB에서 `users.role`을 바꾼다.

### 설정

```yaml
kachi:
  notification:
    routing:
      group-id: notification-routing
      request-topic: notification.requested
      auto-offset-reset: earliest
      topics:
        summary-created: ai.summary.created
        keyword-quarantined: ai.keyword.quarantined
      dlt:
        topic: notification.routing.dlt
      retry:
        max-attempts: 3
        backoff: 1s
      user-service:
        base-url: http://localhost:8080
        subscriptions-path: /api/v1/internal/subscriptions
        users-path: /api/v1/internal/users
        timeout: 3s
        max-in-memory-size: 262144
```

전용 프로세스라 켜고 끄는 스위치는 없다. `base-url`이 비어 있으면 기동 시 실패시킨다.

### consumer offset 초기 위치는 `earliest`다

`auto-offset-reset`은 consumer group에 저장된 offset이 없을 때 파티션의 처음(`earliest`)에서 읽을지, 붙은 시점 이후(`latest`, Kafka 기본값)부터 읽을지 정한다.
한 번 commit한 group은 저장된 offset에서 이어 읽으므로 이 값이 쓰이는 순간은 둘뿐이다. group이 처음 붙을 때, 그리고 offset이 retention으로 사라졌을 때다.

notification 계열 consumer 세 개는 모두 `earliest`다.

| consumer group | topic | 놓치면 생기는 일 |
| --- | --- | --- |
| `notification-routing` | `ai.summary.created`, `ai.keyword.quarantined` | 요약은 만들어졌는데 아무에게도 알림이 가지 않는다 |
| `notification-service` | `notification.requested` | routing이 발행한 요청이 접수되지 않는다. routing job은 COMPLETED라 다시 발행하지도 않는다 |
| `notification-worker` | `notification.dispatch` | 접수된 알림이 발송되지 않는다 (기존 설정) |

여기 topic은 전부 "레코드 1건 = 처리해야 할 일"이다. `latest`는 "지난 것은 의미 없고 지금 이후만 중요한" 스트림에 맞는 값이고, 여기에는 그런 topic이 없다.

routing이 이 topic의 첫 producer가 되면서 유실 경로가 생기기 때문이다. 새 환경에서 routing이 notification-service보다 먼저 떠서 요청을 발행하면,
`notification-service` consumer group이 아직 없으므로 group이 생기는 시점의 `latest`는 이미 쌓인 요청들의 뒤가 된다. 그 요청은 아무도 읽지 않고 사라진다.
routing 쪽 `RoutingJob`은 발행에 성공했으니 COMPLETED로 남아 다시 발행하지도 않는다. 기동 순서에 정확성이 걸리지 않게 `earliest`로 고정한다.

대가는 첫 기동 때 backlog를 한꺼번에 처리한다는 것이다. routing은 그 backlog가 사용자 알림으로 직결되므로 아래 운영 제약에 backlog 확인을 두었다.
notification-service는 `requestId`, worker는 `notificationId` 멱등(ADR 013)이 있어 backlog를 다시 읽어도 중복 발송으로 이어지지 않는다.

### Q1 — requestId로 알림 조회

`GET /api/v1/notifications?requestId=`를 연다. `requestId`가 순수 함수이므로 `(summaryId, userId, channel)`을 아는 쪽은 알림을 바로 찾을 수 있다.
전체 사이클 검증이 이 API로 결과를 확인한다. 응답의 `recipientId`는 사용자 id다.

## 검토한 대안

- **notification-service 안의 패키지 + 직접 호출 (ADR 025 원안)**
  - 위 "검토한 선택지". 접수 서비스와 fan-out의 부하가 결합된다.
- **별도 모듈, 같은 프로세스, 계약 hop**
  - 비용은 내고 격리는 얻지 못한다.
- **routing을 user-service로**
  - 구독 데이터는 거기 있지만 사용자 도메인이 비동기 알림 오케스트레이션을 떠안는다(ADR 025 반려안 유지).
- **routing이 notification-core에 의존**
  - `Notification`·outbox·dispatch 모델을 쓰지 않으면서 끌고 오게 된다. routing의 도메인은 `RoutingJob`뿐이다.
- **routing에 outbox**
  - 원천이 Kafka 레코드라 재전달이 같은 일을 한다. ack 대기 순차 발행이 그 대가다.
- **RoutingJob에 진행 커서**
  - requestId 멱등이 정확성을 보장한다. 커서는 성능 항목이며 페이징과 함께 간다.
- **routing 안에서 user-service 호출을 재시도**
  - 재시도 구동은 영속 상태나 broker가 한다는 원칙(ADR 015)에 어긋난다. Kafka 재전달이 같은 일을 한다.
- **본문을 application 계층에서 렌더링**
  - application이 `ai-contract`에 의존하게 된다. 계약을 아는 것은 어댑터다.
- **출처를 계약에 싣지 않고 `Notification.attributes: Map<String, String>`**
  - 자유 형식이라 타입 보장이 없고 불변 aggregate 규칙(ADR 024)과 맞지 않는다.
- **격리 알림 수신자를 routing 설정에**
  - 처음 이렇게 했었다. 발송 경로가 수신자의 역할을 알게 되고, 설정값이 주소도 참조도 아닌 값이 됐다. 관리자 목록은 user-service의 것이다(ADR 025).
- **격리 알림을 시스템 사용자의 "격리" 키워드 구독으로**
  - 구독은 키워드 단위라 격리 이벤트를 억지로 키워드에 맞추게 된다. 역할 조회가 자연스럽다.
- **quarantineId만 eventKey로**
  - 재격리가 걸러진다.
- **consumer offset 초기 위치를 `latest`로**
  - 기동 순서에 따라 요청이 유실된다. 놓쳐도 되는 topic이 없다.

## 트레이드오프

- 장점:
  - 요약 파이프라인, 라우팅, 접수·발송이 각각 다른 프로세스다. 어느 지점에서 죽어도 알림이 두 번 가지 않고, fan-out이 접수 API를 느리게 하지 않는다.
  - notification-service는 다시 "완성된 요청을 접수·발송한다"만 한다. ai 계약과 user-service를 모른다.
  - 접수·발행·발송의 기존 규칙(ADR 013·015)을 그대로 쓴다. routing이 새로 만든 것은 job 한 컬렉션, requestId 규칙, 계약의 `origin` 필드뿐이다.
  - 주소가 이벤트·저장소·로그에 없다.
- 단점:
  - 요약 1건당 `notification.requested` 메시지가 구독자 × 채널 수만큼 생긴다. 지금 규모에서는 무시할 양이고, 커지면 오히려 이 구조가 필요해진다.
  - `RoutingJob`만 보고 접수·중복 결과를 알 수 없다. Q1과 read model이 대신한다.
  - 로컬에서 띄울 프로세스가 하나 는다.
  - user-service가 죽으면 routing이 밀린다. 재시도 한도(3회, 약 3초) 안에 회복하지 않으면 DLT로 가고 운영자가 재발행해야 한다.
  - 본문의 키워드가 소문자 정규화 값이다.
  - notification-worker의 저장 모델을 함께 바꾼다.
  - 대상이 많은 키워드는 ack 대기 순차 발행이라 느리다.

## 운영 제약

- worker는 `(recipientId, channel)`로 user-service에서 주소를 받아 보낸다. 바인딩이 없거나 해지된 수신자의 알림은 `SUPPRESSED`로 끝난다(ADR 028).
- routing을 처음 켜기 전 `ai.summary.created` backlog를 확인한다. `earliest`라 쌓인 요약이 한꺼번에 알림으로 나간다.
- DLT 메시지의 재처리는 원 topic 재발행이다. `RoutingJob`이 STARTED로 남아 있으므로 다시 발행되고, 뒷단 notification-service의 `requestId` 멱등이 중복 접수를 거른다.
- `routing_jobs`의 eventKey unique index는 `RoutingJobConflictException`의 근거다. local은 `auto-index-creation`으로, 그 밖은 `infra/mongo/notification-routing-indexes.js`로 만든다.
