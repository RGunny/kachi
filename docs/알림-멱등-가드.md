# 알림 멱등 가드

알림 하나가 사용자에게 딱 한 번 가게 하는 장치는 하나가 아니라 넷이다. Kafka는 at-least-once라 같은 메시지가 두 번 올 수 있고, worker는 vendor를 부른 뒤 결과를 저장하기 전에 죽을 수 있다. 각 층은 서로 다른 상황을 막으므로 "다른 층이 있으니 이 층은 필요 없다"는 판단은 성립하지 않는다. 이 문서는 네 층이 각각 무엇을 막고 어디서 풀리는지 한곳에 모은다.

```
producer ──▶ notification-service ──▶ Kafka ──▶ notification-worker ──▶ vendor
                  ①                                 ②      ③  ④
```

| 층 | 어디에 | 키 | 막는 상황 | 실패하면 |
| --- | --- | --- | --- | --- |
| ① 접수 requestId | notification-service, Redis SETNX(24시간) 다음 Mongo unique index | `notification:request:{requestId}`, `requestId` | 같은 요청이 두 번 접수돼 `Notification`이 둘 생기는 것 | 두 번째 접수를 중복으로 응답한다 (ADR 013) |
| ② dispatch dedupe | worker, Redis SETNX | `notification:dispatch:{notificationId}` | 같은 dispatch 메시지가 두 worker에서 동시에 실행되는 것 | 이번 소비를 `duplicated`로 끝내고 ack한다 |
| ③ vendor idempotency key | worker, Redis에 notificationId당 하나 | `SendNotificationCommand.idempotencyKey` | 그 키를 존중하는 vendor에서 같은 호출이 두 번 처리되는 것 | vendor가 거른다. 지금 붙어 있는 세 채널은 키를 받지 않는다 |
| ④ sent 가드 | worker, Redis SETNX, `send` 직전 | `notification:sent:{requestId}` | vendor 호출은 끝났는데 결과 저장 전에 worker가 죽어, stale 회수 뒤 같은 알림이 한 번 더 나가는 것 | `SUPPRESSED`, 사유 `already sent` (ADR 028) |

## 층별로 보는 이유

**①은 알림의 개수를 지킨다.** routing이 같은 이벤트를 다시 처리하거나 외부 producer가 재전송해도 `Notification`은 하나다. 그 뒤 층은 모두 "그 하나가 두 번 나가지 않게" 한다.

**②는 동시 실행을 막는다.** Kafka 재전달이나 리밸런스로 같은 dispatch 메시지를 두 worker가 쥐면 한쪽만 claim에 들어간다. 이 마커는 `RETRY_WAIT`로 확정할 때 풀린다 — 다음 재시도가 다시 잡아야 하기 때문이다. 그래서 회수 뒤의 재발송은 이 층이 막지 못한다.

**③은 vendor 쪽 방어다.** 재시도마다 같은 값이 되도록 worker가 notificationId당 하나를 만들어 Redis에 두고 sender에 넘긴다. 키를 받는 vendor API에서만 동작하는데, Slack·Discord incoming webhook과 Telegram Bot API는 받지 않으므로 지금은 어느 sender도 vendor에 전달하지 않는다. 키를 받는 채널을 붙일 때 쓸 자리다.

**④는 회수 뒤 재발송을 막는다.** 시나리오는 이렇다.

```
worker A: claim(PROCESSING) → resolve → send(vendor 200) → [죽음]
recovery: stale PROCESSING → RETRY_WAIT
worker B: claim(PROCESSING) → resolve → sent 가드 SETNX 실패 → SUPPRESSED("already sent")
```

가드가 없으면 worker B가 같은 알림을 한 번 더 보낸다. ①은 `Notification`이 하나라 관여하지 않고, ②는 `RETRY_WAIT`에서 풀렸고, ③은 지금 채널에서 무력하다.

## 가드 ④의 창

가드는 `send` 직전에 잡는다. 가드를 잡고 호출 전에 죽으면 그 알림은 회수 뒤 `SUPPRESSED`로 끝나 유실된다. 창을 `send` 직전으로 좁힌 것은 이 유실을 최소로 하기 위해서다. 이중 발송과 유실 중 이중 발송이 사용자에게 더 나쁘다고 판단했다 — 놓친 알림은 다음 요약에서 회복되지만 두 번 온 알림은 사용자가 바로 본다. 근거는 ADR 028.

## 언제 풀리는가

| 층 | 풀리는 시점 |
| --- | --- |
| ① | 풀리지 않는다. 영구 |
| ② | `RETRY_WAIT` 확정 뒤, 예상 밖 예외로 빠져나갈 때. `SENT`·`DEAD`·`SUPPRESSED`는 TTL 만료 |
| ③ | TTL 만료(`idempotency-key-ttl`, 24h) |
| ④ | `RETRY_WAIT` 확정 뒤, `send` 도중 예상 밖 예외로 빠져나갈 때. `SENT`·`DEAD`·`SUPPRESSED`와 stale finalize는 TTL 만료(③과 같은 24h) |

`SENT`에서 ④를 풀지 않는 것이 이 가드의 목적이다. `DEAD`·`SUPPRESSED`는 종착이라 다시 나갈 일이 없고, stale finalize(claim이 다른 worker로 넘어간 뒤의 늦은 결과)는 그 worker의 결과를 따른다.

## 운영에서

- ④의 키를 손으로 지우면 그 알림이 다시 나갈 수 있다. 재발송이 목적일 때만 지운다.
- `DEAD`를 `recoverDeadToRequested`로 되살리면 새 dispatch outbox가 생기지만 `requestId`는 같다. 24h 안이라면 ④에 걸려 `SUPPRESSED`가 된다 — 실제로 vendor까지 갔던 알림이면 그것이 맞는 결과이고, 가지 않았던 알림(예: 주소 조회 실패로 `DEAD`)이면 ④ 키가 없어 정상 발송된다.
- 지표: `kachi_notification_dispatch_total{result="duplicated"}`가 ②, `{result="suppressed"}`가 ④와 주소 없는 스킵을 함께 센다. 둘을 나누려면 `failureReason`을 본다.
