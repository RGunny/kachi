# Kachi Architecture

## Architecture Style

Kachi는 서비스별로 Hexagonal Architecture를 따른다.

```text
External Actor
    -> Adapter In
    -> Application Port In
    -> Application Service
    -> Domain
    -> Application Port Out
    -> Adapter Out
    -> External System
```

## Package Rule

기본 패키지는 다음 규칙을 따른다.

```text
me.rgunny.kachi.{service}
```

예시는 다음과 같다.

```text
me.rgunny.kachi.user
me.rgunny.kachi.collector
me.rgunny.kachi.ai
me.rgunny.kachi.notification
me.rgunny.kachi.history
```

각 서비스 내부 패키지는 다음 구조를 기본으로 한다.

```text
me.rgunny.kachi.{service}
├── domain
├── application
│   ├── port
│   │   ├── in
│   │   └── out
│   └── service
├── adapter
│   ├── in
│   └── out
└── config
```

## Layer Responsibility

### Domain

- 순수 도메인 모델, 값 객체, enum, 도메인 규칙을 둔다.
- Spring, JPA, Redis, Kafka, WebClient 같은 기술에 의존하지 않는다.
- 도메인 행위와 불변식을 최대한 이 계층에 둔다.

### Application

- 유스케이스를 표현한다.
- `port.in`에는 외부에서 호출할 유스케이스 인터페이스와 command/query를 둔다.
- `port.out`에는 DB, Redis, 외부 API, 메시징 등 외부 의존을 추상화한 포트를 둔다.
- `service`에는 유스케이스 구현체를 둔다.

### Adapter In

- HTTP controller, Kafka listener, scheduler 등 외부 요청 진입점을 둔다.
- 요청 DTO를 application command/query로 변환한다.
- 도메인 규칙을 직접 구현하지 않는다.
- HTTP API 버전은 adapter in의 외부 계약으로 관리한다.

### Adapter Out

- Persistence, Redis, 외부 API client, Kafka publisher, LLM client 등 외부 시스템 연동을 둔다.
- application `port.out`을 구현한다.
- Spring Data repository와 entity는 이 계층에 둔다.

### Config

- Spring bean wiring, properties, security 설정 등 프레임워크 설정을 둔다.

## Dependency Rule

의존 방향은 안쪽을 향해야 한다.

```text
adapter -> application -> domain
```

금지하는 의존은 다음과 같다.

- `domain`이 `application`에 의존
- `domain`이 `adapter`에 의존
- `application`이 `adapter`에 의존
- Spring Data repository를 `domain`에 직접 배치

## API 버전 정책

HTTP API는 URL path segment 방식으로 버전을 표현한다.

```text
/api/v1/{resource}
```

현재 지원 버전은 `v1`이다.

`user-service`는 Spring MVC의 API versioning 설정을 사용한다.

- 전역 path prefix는 `ApiVersionConfig`에서 설정한다.
- 지원 버전 문자열은 `ApiVersions`에 모은다.
- 컨트롤러는 리소스 경로만 선언하고 `/api` prefix를 직접 갖지 않는다.
- 각 handler method는 `version = ApiVersions.V1`로 자신이 제공하는 API 계약 버전을 명시한다.

예시는 다음과 같다.

| 기능 | Method | Path |
| --- | --- | --- |
| 사용자 등록 | `POST` | `/api/v1/users` |
| 관심 키워드 등록 | `POST` | `/api/v1/users/{userId}/keywords` |
| 관심 키워드 수정 | `PATCH` | `/api/v1/keywords/{keywordId}` |

버전은 환경별 설정값이 아니라 코드와 함께 배포되는 API 계약이다. 따라서 `application.yaml`로 분리하지 않고, 컴파일 타임 상수로 관리한다.

## Architecture Verification

아키텍처 의존 규칙은 ArchUnit 테스트로 검증한다.

우선 검증할 규칙은 다음과 같다.

- `domain`은 `application`, `adapter`, `config`에 의존하지 않는다.
- `application`은 `adapter`, `config`에 의존하지 않는다.
- `adapter.in`에는 Controller, messaging listener, scheduler 같은 진입 어댑터를 둔다.
- `adapter.out`에는 persistence, Redis, 외부 API client, message publisher 같은 외부 연동 어댑터를 둔다.
- Spring Data repository와 persistence entity는 `adapter.out.persistence`에 둔다.
- 각 서비스는 필요한 경우 `ArchitectureTest`를 두고 패키지 의존 규칙을 자동 검증한다.

## Service Boundaries

| Service | Boundary |
| --- | --- |
| user-service | 사용자 인증, 사용자 상태, 관심 키워드 관리 |
| collector-service | 외부 뉴스/시장 데이터 수집 |
| ai-service | LLM 기반 키워드 확장과 뉴스 요약 |
| notification-service | 알림 발송, outbox, 재시도, 채널별 전송 |
| history-service | 장기 이력 저장, 사용자별 조회, 통계 집계 |

서비스는 다른 서비스의 DB를 직접 읽거나 쓰지 않는다. 필요한 데이터는 API, 메시지, 또는 명시적인 동기화 흐름을 통해 전달한다.
