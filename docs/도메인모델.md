# Kachi 도메인 모델

## 도메인 이야기

Kachi는 관심 키워드로 뉴스를 받아보는 서비스다. 
까치가 소식을 물어다 주듯, 사용자가 등록한 키워드에 맞는 뉴스를 모아 AI가 요약하고 알림으로 전해준다.

- 사용자는 회원으로 등록하고(로컬 또는 OAuth), 관심 키워드를 등록한다.
  "나는 '삼성전자'와 '금리' 소식을 받아보고 싶다."
- 수집기는 활성 키워드를 기준으로 여러 뉴스 provider에서 주기적으로 뉴스를 수집한다.
  같은 기사가 여러 번 저장되지 않도록 URL과 제목으로 중복을 걸러내고,
  한 번의 수집이 어떻게 끝났는지(성공/부분 실패/실패)를 실행 기록으로 남긴다.
- AI는 수집된 뉴스를 키워드별로 묶어 LLM으로 요약한다. 요약은 구간(window) 단위로 진행되며, 
  어디까지 처리했는지를 watermark로 기억해 중단 후에도 이어서 처리한다.
  같은 뉴스 묶음을 다시 요약하지 않도록 newsHash로 중복을 막고, 반복 실패하는 키워드는 격리해 전체 진행을 막지 않게 한다.
- 요약이 만들어지면 알림으로 발송한다. 알림은 접수부터 채널 발송까지 상태 기계로 추적되며, 
  유실을 막는 outbox와 실패를 분류해 재시도하는 정책을 갖는다.
  발송 채널은 Slack, Discord, Telegram 등이다.
- (계획) 사용자별 뉴스·요약·알림 결과는 장기 이력으로 적재해 조회와 통계에 쓴다.

## 컨텍스트 맵

프로젝트 파이프라인 흐름이다. 
화살표는 데이터가 흐르는 방향이며, HTTP internal 구간은 소비하는 쪽이 호출(pull)하고 Kafka 구간은 만드는 쪽이 발행(push)한다.

```text
 사용자                   외부 뉴스 provider               LLM provider
   │ 키워드 등록·조회       (Google·Naver·Finnhub)         (OpenAI 호환, Groq 등)
   │ (HTTP /api/v1)             │ 뉴스 수집                     │ 뉴스 요약
   ▼                           ▼                              ▼
 ┌──────────────┐  활성 키워드   ┌───────────────────┐ 수집 뉴스  ┌──────────────┐
 │ user-service │────────────▶│ collector-service │─────────▶│  ai-service  │
 │ MySQL·Redis  │   (HTTP     │      MongoDB      │  (HTTP   │   MongoDB    │
 └──────────────┘   internal) └───────────────────┘ internal)└──────┬───────┘
                                                                    │ notification.requested
                                                                    │ (Kafka — 단계 F 연결 예정)
                                                                    ▼
                                                     ┌──────────────────────┐
                                                     │ notification-service │
                                                     │   MongoDB RS·Redis   │
                                                     └──────────┬───────────┘
                                                                │ notification.dispatch
                                                                │ (Kafka, outbox 발행 보장)
                                                                ▼
                                                     ┌──────────────────────┐
                                                     │ notification-worker  │
                                                     └──────────┬───────────┘
                                                                │ 채널 발송
                                                                ▼
                                                  Slack·Discord·Telegram ──▶ 사용자
```

- ai-service도 collector와 같은 활성 키워드 internal API를 조회한다 (그림에서는 생략).
  실제 포트·endpoint 계약은 [포트-구성.md](포트-구성.md)에 있다.
- history-service(미구현)는 요약·알림 결과를 장기 이력으로 적재하는 소비자로 이 지도에 추가될 예정이다.

## Bounded Context

| 컨텍스트 | 모듈 | 책임 | 상세 문서 |
| --- | --- | --- | --- |
| User | user-service | 사용자 인증, 사용자 상태, 관심 키워드 관리 | [도메인모델-user.md](도메인모델-user.md) |
| Collector | collector-service | 외부 뉴스/시장 데이터 수집 및 저장 | [도메인모델-collector.md](도메인모델-collector.md) |
| AI | ai-service | 뉴스 요약, 키워드 확장, watermark/격리 운영 | [도메인모델-ai.md](도메인모델-ai.md) |
| Notification | notification-core/-service/-worker | 알림 접수, outbox, 채널 발송, 재시도 | [도메인모델-notification.md](도메인모델-notification.md) |
| History | (미구현) | 사용자별 장기 이력 적재와 통계 | [도메인모델-history.md](도메인모델-history.md) |

컨텍스트는 bounded context로 독립이다. 어휘가 비슷해도 코드를 공유하지 않는다
(예: ai의 `LlmFailure`와 notification의 `RetryFailure`는 taxonomy 규약만 정렬한 별개 모델 — ADR 021).
서비스 간 공유 모듈은 `notification-contract` 하나뿐이다.

## 도메인 모델 만들기

새 개념을 모델에 추가할 때는 다음 순서를 따른다.

1. 듣고 배우기 — 요구와 운영 시나리오에서 출발한다
2. '중요한 것'들 찾기 — 개념 식별
3. '연결 고리' 찾기 — 관계 정의
4. '것'들을 설명하기 — 속성과 기본 행위 명시
5. 그려보기 — 시각화 (상태 기계는 ASCII 다이어그램)
6. 이야기하고 다듬기 — 반복

새 개념은 코드보다 먼저 이 문서 계열과 [용어사전](용어사전.md)에 자리를 잡는다.
아직 구현하지 않은 개념도 계획으로 등재하고 미구현임을 표시한다.

## 공통 모델 관례

컨텍스트별 문서에서 반복하지 않는 공통 규칙이다. 구현 관례의 전체 목록은
[개발가이드.md](개발가이드.md)에 있다.

- **생성과 복원의 분리**: aggregate/entity는 `private constructor`와 정적 팩터리만 갖는다.
  신규 생성(`create`, `start`, `register`, `request`, `track`, `initial`)은 불변식을 검증하고
  초기 상태를 결정하며, 저장소 조회 결과 복원은 `restore()`를 쓴다.
- **식별자**: aggregate 식별자는 `@JvmInline value class` id VO다. `newId()`는 시간 정렬
  UUID(v7)를 생성하므로 id 순서가 곧 생성 순서다(ADR 003). 다른 aggregate의 id와
  UUID 값을 직접 섞어 쓰지 않는다.
- **시간**: 도메인은 현재 시각을 스스로 만들지 않는다. application 계층이 `Clock`으로
  생성한 `Instant`를 파라미터로 전달받는다.
- **값 객체**: `of()` 정적 팩터리에서 정규화(trim, lowercase 등)와 검증을 마친 뒤 생성한다.
  불변식 위반은 `require`로 즉시 실패시킨다.
- **불변성**: user/collector/ai의 도메인 객체는 불변이며 상태 변경은 새 인스턴스를
  반환한다. notification의 상태 기계 aggregate(`Notification`, `NotificationOutbox`,
  `NotificationDltMessage`)는 `private set` 가변 프로퍼티로 전이를 표현한다 —
  두 모양의 차이는 의도된 것이다.
- **스테레오타입 표기**: 컨텍스트 문서의 각 요소는 _Aggregate Root_, _Entity_,
  _Value Object_, _Enum_, _Domain Service_ 로 표기한다.
