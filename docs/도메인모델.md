# Kachi Domain Model

## Domain Overview

Kachi는 사용자가 등록한 관심 키워드를 기준으로 뉴스와 시장 데이터를 수집하고, AI로 키워드를 확장하거나 뉴스를 요약한 뒤, 사용자가 설정한 채널로 알림을 발송하는 서비스다.

서비스는 다음 bounded context로 나눈다.

| Context | Service | Responsibility |
| --- | --- | --- |
| User | user-service | 사용자 인증, 사용자 상태, 관심 키워드 관리 |
| Collector | collector-service | 외부 뉴스/시장 데이터 수집 및 저장 |
| AI | ai-service | 키워드 확장, 뉴스 요약, 감성 판단 |
| Notification | notification-service | 알림 요청 접수, outbox, 채널별 발송, 재시도 |
| History | history-service | 사용자별 뉴스/요약/알림 이력 적재 및 통계 집계 |

## User Aggregate

### User

_Aggregate Root_

#### Attributes

- `id`: 사용자 식별자
- `email`: 로그인 이메일
- `nickname`: 사용자 표시 이름
- `status`: 사용자 상태
- `role`: 사용자 권한
- `authProvider`: 인증 제공자
- `providerUserId`: OAuth provider가 제공하는 사용자 식별자
- `registeredAt`: 가입 일시
- `lastLoginAt`: 마지막 로그인 일시
- `deactivatedAt`: 탈퇴 일시

#### Behaviors

- `register()`: 사용자를 등록한다.
- `restore()`: 저장소에 있던 사용자 상태를 도메인 객체로 복원한다.
- `activate()`: 사용자를 활성화한다.
- `recordLogin()`: 로그인 성공 시각을 기록한다.
- `deactivate()`: 사용자를 탈퇴 상태로 변경한다.

#### Rules

- 이메일은 중복될 수 없다.
- 신규 등록은 `register()`를 사용하고, 저장소 조회 결과 복원은 `restore()`를 사용한다.
- `register()`, `recordLogin()`, `deactivate()`에 필요한 현재 시각은 application 계층에서 `Clock`으로 생성해 `Instant`로 전달한다.
- 활성 사용자만 키워드를 등록, 수정, 삭제할 수 있다.
- 활성 사용자만 로그인 시각을 기록할 수 있다.
- 탈퇴 사용자는 키워드를 변경할 수 없다.
- OAuth 사용자는 인증 제공자와 provider user id로 식별할 수 있어야 한다.
- LOCAL 사용자는 provider user id를 가지지 않는다.

### Email

_Value Object_

#### Attributes

- `value`: 이메일 주소

#### Behaviors

- `of()`: 문자열을 정규화하고 이메일 값 객체를 생성한다.

#### Rules

- 이메일은 빈 값일 수 없다.
- 이메일은 소문자로 정규화한다.
- 이메일은 255자를 초과할 수 없다.

### Keyword

_Entity_

#### Attributes

- `id`: 키워드 식별자
- `userId`: 키워드를 소유한 사용자 식별자
- `name`: 키워드 이름
- `enabled`: 수집 대상 포함 여부
- `registeredAt`: 키워드 등록 일시
- `disabledAt`: 키워드 비활성화 일시

#### Behaviors

- `create()`: 키워드를 등록한다.
- `restore()`: 저장소에 있던 키워드 상태를 도메인 객체로 복원한다.
- `rename()`: 키워드 이름을 변경한다.
- `enable()`: 키워드를 수집 대상으로 포함한다.
- `disable()`: 키워드를 수집 대상에서 제외한다.

#### Rules

- 키워드는 반드시 한 명의 사용자에게 속한다.
- 한 사용자는 같은 이름의 키워드를 중복 등록할 수 없다.
- 신규 등록은 `create()`를 사용하고, 저장소 조회 결과 복원은 `restore()`를 사용한다.
- `create()`와 `disable()`에 필요한 현재 시각은 application 계층에서 `Clock`으로 생성해 `Instant`로 전달한다.
- 비활성 키워드는 뉴스 수집 대상에서 제외된다.
- 이미 비활성화된 키워드는 다시 비활성화할 수 없다.

## Collector Context

### News

_Aggregate Root_

#### Attributes

- `id`: 뉴스 식별자
- `source`: 뉴스 출처
- `title`: 제목
- `url`: 원문 URL
- `urlHash`: URL 중복 확인용 hash
- `titleFingerprint`: 제목 기반 중복 후보 확인용 fingerprint
- `publishedAt`: 발행 시각
- `collectedAt`: 수집 시각
- `matchedKeywords`: 이 뉴스와 매칭된 수집 키워드 목록

#### Rules

- 제목과 URL이 없는 뉴스는 저장하지 않는다.
- 매칭 키워드는 하나 이상이어야 한다.
- 같은 뉴스가 여러 키워드에 매칭될 수 있다.
- 중복 키워드는 제거한다.
- URL hash와 제목 fingerprint는 중복 후보를 줄이기 위한 값이다.
- 실제 저장 중복 방어는 persistence 계층의 unique index에서 처리한다.
- 제목의 의미 기반 중복 판단은 collector 도메인에서 과하게 처리하지 않는다.

### NewsId

_Value Object_

#### Attributes

- `value`: 뉴스 식별 UUID

#### Behaviors

- `newId()`: 신규 뉴스 식별자를 생성한다.
- `of()`: 저장소에 있던 UUID를 뉴스 식별자로 복원한다.

#### Rules

- 뉴스 식별자는 `NewsId` 타입으로 표현한다.

### NewsTitle

_Value Object_

#### Attributes

- `value`: 뉴스 제목
- `fingerprint`: 제목 기반 중복 후보 확인용 fingerprint

#### Behaviors

- `of()`: 문자열을 정규화하고 뉴스 제목 값 객체를 생성한다.

#### Rules

- 제목은 빈 값일 수 없다.
- 제목 앞뒤 공백은 제거한다.
- 초기 구현에서는 제목 길이, 금칙어, 의미 기반 정합성을 강하게 검증하지 않는다.
- fingerprint는 대소문자와 연속 공백 차이를 줄여 계산한다.
- fingerprint는 URL이 다른 유사 제목 뉴스를 찾기 위한 후보값이며, 저장을 막는 강한 중복 키로 직접 사용하지 않는다.

### NewsUrl

_Value Object_

#### Attributes

- `value`: 뉴스 원문 URL
- `hash`: URL 중복 확인용 hash

#### Behaviors

- `of()`: 문자열을 정규화하고 URL 값 객체를 생성한다.

#### Rules

- URL은 빈 값일 수 없다.
- URL 앞뒤 공백은 제거한다.
- 초기 구현에서는 URL 문법을 강하게 검증하지 않는다.
- provider별 URL 보정이 필요하면 adapter 계층에서 처리한다.

### CollectedKeyword

_Value Object_

#### Attributes

- `value`: 수집 기준 키워드

#### Behaviors

- `of()`: 문자열을 정규화하고 수집 키워드 값 객체를 생성한다.

#### Rules

- 수집 키워드는 빈 값일 수 없다.
- 수집 키워드 앞뒤 공백은 제거한다.

### CollectionRun

_Aggregate Root_

수집 작업 한 번의 실행 기록이다.

`CollectionRun`은 장기 조회용 이력이나 `history-service`로 보내는 사용자 이력이 아니다. collector가 scheduler, 수동 API, 이벤트 등으로 수집을 한 번 시작했을 때의 실행 중 상태와 완료 결과를 표현한다.

#### Attributes

- `id`: 수집 실행 식별자
- `targetType`: 수집 대상 유형 (`NEWS`, `MARKET_DATA`)
- `status`: 실행 상태 (`RUNNING`, `SUCCEEDED`, `PARTIALLY_FAILED`, `FAILED`)
- `startedAt`: 시작 시각
- `finishedAt`: 종료 시각
- `requestedKeywords`: 수집 대상 키워드 수
- `collectedCount`: 신규 저장 건수
- `duplicateCount`: 중복 제외 건수
- `failureCount`: 실패 provider 수
- `failureReason`: 실패 사유 요약
- `providerResults`: provider별 수집 결과

#### Behaviors

- `start()`: 수집 실행을 시작한다.
- `restore()`: 저장소에 있던 수집 실행 상태를 도메인 객체로 복원한다.
- `complete()`: provider별 결과를 기준으로 수집 실행을 완료한다.

#### Rules

- 수집 실행은 `RUNNING` 상태로 시작한다.
- `RUNNING` 상태의 수집 실행만 완료할 수 있다.
- 완료 시각은 시작 시각보다 이전일 수 없다.
- 모든 provider가 성공하면 `SUCCEEDED`로 완료한다.
- 일부 provider만 실패하면 `PARTIALLY_FAILED`로 완료한다.
- 모든 provider가 실패하거나 provider 결과가 없으면 `FAILED`로 완료한다.
- 신규 저장 건수, 중복 제외 건수, 실패 provider 수는 provider별 결과에서 계산한다.
- `CollectionRun`은 실패한 외부 provider 때문에 전체 애플리케이션 흐름이 끊겼는지 확인하고 재처리 여부를 판단하기 위한 운영 기준이다.

### CollectionRunId

_Value Object_

#### Attributes

- `value`: 수집 실행 식별 UUID

#### Behaviors

- `newId()`: 신규 수집 실행 식별자를 생성한다.
- `of()`: 저장소에 있던 UUID를 수집 실행 식별자로 복원한다.

#### Rules

- 수집 실행 식별자는 `CollectionRunId` 타입으로 표현한다.

### ProviderCollectionResult

_Value Object_

provider 하나의 수집 결과다.

#### Attributes

- `source`: 뉴스 provider
- `status`: provider 수집 상태 (`SUCCEEDED`, `FAILED`)
- `fetchedCount`: provider에서 가져온 원본 건수
- `savedCount`: 신규 저장 건수
- `duplicateCount`: 중복 제외 건수
- `failureReason`: 실패 사유 분류
- `failureMessage`: 실패 메시지

#### Behaviors

- `success()`: provider 성공 결과를 생성한다.
- `failure()`: provider 실패 결과를 생성한다.

#### Rules

- 성공 결과의 수집/저장/중복 건수는 0 이상이어야 한다.
- 성공 결과는 실패 사유와 실패 메시지를 갖지 않는다.
- 실패 결과는 실패 사유와 실패 메시지를 가져야 한다.
- 실패한 provider는 저장/중복 건수를 0으로 기록한다.

### NewsSource

_Enum_

뉴스를 가져온 provider를 구분한다.

Values:

- `GOOGLE`: Google News RSS
- `NAVER`: Naver Search API 뉴스 검색
- `FINNHUB`: Finnhub Company News

Provider별 응답 구조, 인증 방식, URL 보정은 adapter 계층에서 처리하고, application/domain 계층은 `NewsSource`와 `CollectedArticle`만 다룬다.

### ProviderFailureReason

_Enum_

provider 수집 실패 사유 분류다.

Values:

- `TIMEOUT`: provider 응답 지연 또는 timeout
- `RATE_LIMITED`: provider rate limit 또는 quota 제한
- `CLIENT_ERROR`: 잘못된 요청, 인증 실패 같은 4xx 계열 오류
- `SERVER_ERROR`: provider 5xx 계열 오류
- `NETWORK_ERROR`: 연결 실패, DNS 오류 같은 네트워크 오류
- `INVALID_RESPONSE`: 응답 파싱 실패 또는 필수 필드 누락
- `UNKNOWN`: 아직 분류하지 못한 오류

### MarketData

_Aggregate Root_

#### Rules

- 시장 데이터는 뉴스 요약의 보조 정보로 사용한다.
- 외부 API 실패는 전체 수집 흐름을 중단시키지 않고 실패 이력으로 남긴다.

## AI Context

### KeywordExpansion

_Aggregate Root_

키워드 하나를 LLM으로 확장한 결과다.

#### Attributes

- `id`: 키워드 확장 식별자
- `keyword`: 원본 키워드
- `expandedKeywords`: 확장 키워드 목록
- `provider`: LLM provider
- `model`: LLM model
- `promptVersion`: 프롬프트 버전
- `createdAt`: 생성 시각

#### Rules

- 확장 키워드는 원본 키워드와 함께 추적되어야 한다.
- 확장 키워드는 빈 값일 수 없다.
- 원본 키워드와 같은 확장 키워드는 제거한다.
- 중복 확장 키워드는 제거한다.
- LLM 응답이 비어 있거나 파싱할 수 없으면 실패로 처리하고 결과를 저장하지 않는다.
- 같은 원본 키워드, prompt version, model 조합은 중복 저장하지 않는다.

### NewsSummary

_Aggregate Root_

키워드별 뉴스 묶음을 LLM으로 요약한 결과다.

#### Attributes

- `id`: 요약 식별자
- `keyword`: 요약 기준 키워드
- `sourceNewsIds`: 요약 대상 뉴스 식별자 목록
- `newsHash`: 요약 대상 뉴스 묶음 중복 확인용 hash
- `title`: 요약 제목
- `content`: 요약 본문
- `sentiment`: 감성 (`POSITIVE`, `NEUTRAL`, `NEGATIVE`, `UNKNOWN`)
- `provider`: LLM provider
- `model`: LLM model
- `promptVersion`: 프롬프트 버전
- `tokenUsage`: 사용 token 수
- `createdAt`: 생성 시각

#### Rules

- 요약은 어떤 뉴스 묶음에서 생성되었는지 추적할 수 있어야 한다.
- 요약 결과에는 사용한 LLM provider와 생성 시각을 남긴다.
- 요약 대상 뉴스는 하나 이상이어야 한다.
- 요약 제목과 본문은 빈 값일 수 없다.
- 같은 키워드, news hash, prompt version, model 조합은 중복 저장하지 않는다.
- LLM 응답이 비어 있거나 필수 필드를 파싱할 수 없으면 실패로 처리하고 결과를 저장하지 않는다.
- news hash가 달라지면 같은 키워드라도 새 요약으로 저장할 수 있다.

### AiRun

_Aggregate Root_

AI 작업 한 번의 실행 기록이다.

#### Attributes

- `id`: AI 실행 식별자
- `targetType`: 실행 대상 유형 (`KEYWORD_EXPANSION`, `NEWS_SUMMARY`)
- `status`: 실행 상태 (`RUNNING`, `SUCCEEDED`, `PARTIALLY_FAILED`, `FAILED`)
- `startedAt`: 시작 시각
- `finishedAt`: 종료 시각
- `requestedKeywords`: 요청 키워드 수
- `succeededCount`: 성공 처리 건수
- `failureCount`: 실패 처리 건수
- `failureReason`: 실패 사유 요약
- `provider`: LLM provider
- `model`: LLM model
- `promptVersion`: 프롬프트 버전

#### Rules

- AI 실행은 `RUNNING` 상태로 시작한다.
- `RUNNING` 상태의 실행만 완료할 수 있다.
- 완료 시각은 시작 시각보다 이전일 수 없다.
- 모든 키워드 처리가 성공하면 `SUCCEEDED`로 완료한다.
- 일부 키워드가 실패하면 `PARTIALLY_FAILED`로 완료한다.
- 모든 키워드가 실패하거나 처리 대상이 없으면 `FAILED`로 완료한다.
- `AiRun`은 notification/history 장기 이력이 아니라 AI 처리 운영 기록이다.

### AiFailureReason

_Enum_

AI provider 또는 AI 처리 실패 사유 분류다.

Values:

- `TIMEOUT`: provider 응답 지연 또는 timeout
- `RATE_LIMITED`: provider rate limit 또는 quota 제한
- `CLIENT_ERROR`: 잘못된 요청, 인증 실패 같은 4xx 계열 오류
- `SERVER_ERROR`: provider 5xx 계열 오류
- `NETWORK_ERROR`: 연결 실패, DNS 오류 같은 네트워크 오류
- `INVALID_RESPONSE`: 응답 파싱 실패 또는 필수 필드 누락
- `EMPTY_INPUT`: 요약 대상 뉴스나 확장 대상 키워드가 없음
- `UNKNOWN`: 아직 분류하지 못한 오류

## Notification Context

### Notification

_Aggregate Root_

알림 요청 한 건의 접수, dispatch 발행, worker 발송 상태를 표현한다.

#### Attributes

- `id`: 알림 식별자
- `requestId`: upstream 요청 멱등 키
- `requester`: 요청 주체
- `channel`: 발송 채널
- `recipient`: 수신자
- `message`: 발송 메시지
- `requestedAt`: 요청 접수 시각
- `status`: 알림 상태
- `failureReason`: 마지막 실패 사유
- `updatedAt`: 마지막 변경 시각
- `lastTransitionAt`: 마지막 상태 전이 시각
- `dispatchAttempts`: vendor 발송 시도 횟수

#### Behaviors

- `request()`: 알림을 `REQUESTED` 상태로 접수한다.
- `markPublished()`: dispatch message 발행 성공을 기록한다.
- `markPublishFailed()`: dispatch message 발행 실패를 기록한다.
- `markProcessing()`: worker가 발송 처리 권한을 획득했음을 기록한다.
- `markSent()`: 외부 채널 발송 성공을 기록한다.
- `markFailed()`: 외부 채널 발송 실패를 기록하고 시도 횟수를 증가시킨다.
- `markRetryWait()`: 자동 재시도 대기 상태로 전이한다.
- `markDead()`: 자동 재시도 종료 상태로 전이한다.

#### Rules

- 신규 알림은 `REQUESTED` 상태로 시작한다.
- dispatch 발행 성공은 `REQUESTED` 또는 `PUBLISH_FAILED`에서만 `PUBLISHED`로 전이한다.
- dispatch 발행 실패는 `REQUESTED`에서 `PUBLISH_FAILED`로 전이한다.
- worker 발송은 `PUBLISHED` 또는 `RETRY_WAIT`에서만 `PROCESSING`으로 claim할 수 있다.
- 발송 성공은 `PROCESSING`에서 `SENT`로 전이한다.
- 발송 실패는 `PROCESSING`에서 `FAILED`로 전이한 뒤 `RETRY_WAIT` 또는 `DEAD`로 갈라진다.
- `SENT`와 `DEAD`는 자동 처리의 종착 상태다.
- `dispatchAttempts`는 sender 결과를 확정할 때 증가한다.
- 상태 전이는 `NotificationHistory`로 기록한다.
- adapter는 상태를 직접 조작하지 않고 core use case를 통해 변경한다.

### NotificationStatus

_Enum_

#### Values

- `REQUESTED`: 요청 수신, 멱등 통과, 영속 완료
- `PUBLISHED`: `notification.dispatch` 발행 성공, worker 진입 가능
- `PUBLISH_FAILED`: `notification.dispatch` 발행 실패, outbox recovery 대상
- `PROCESSING`: worker가 발송 claim 후 sender 호출 진행 중
- `FAILED`: sender 호출 실패, `RETRY_WAIT` 또는 `DEAD` 분기 직전
- `RETRY_WAIT`: retry topic/backoff 후 재시도 가능한 상태
- `SENT`: 외부 채널 발송 성공
- `DEAD`: 자동 재시도 종료, 운영자 수동 재처리 대상

### NotificationOutbox

_Aggregate Root_

요청 접수와 worker용 dispatch message 발행 사이의 유실을 막는 발행 보장 대기열이다.

#### Attributes

- `id`: outbox 식별자
- `notificationId`: 발행 대상 알림 식별자
- `topic`: 발행할 Kafka topic
- `partitionKey`: Kafka partition key
- `eventPayload`: 직렬화된 dispatch message
- `createdAt`: 생성 시각
- `outboxStatus`: outbox 발행 상태
- `retryCount`: 발행 실패 재시도 횟수
- `nextRetryAt`: 다음 재시도 가능 시각
- `lastError`: 마지막 발행 실패 사유
- `publishedAt`: 발행 성공 시각
- `claimedAt`: 발행 claim 시각
- `claimedBy`: 발행 claim 주체

#### Behaviors

- `create()`: `PENDING` outbox를 생성한다.
- `markPublishing()`: 발행 처리 권한을 획득한다.
- `markPublished()`: Kafka 발행 성공을 기록한다.
- `recordFailure()`: Kafka 발행 실패를 기록하고 `PENDING` 또는 `DEAD`로 전이한다.
- `markDead()`: 즉시 자동 재시도 종료 상태로 전이한다.
- `recoverToPending()`: 운영자 복구로 `DEAD`를 `PENDING`으로 되돌린다.

#### Rules

- 알림 요청 접수와 dispatch outbox 저장은 같은 저장 경계에서 확정한다.
- `PENDING` outbox만 `PUBLISHING`으로 claim할 수 있다.
- `PUBLISHING` outbox만 `PUBLISHED`, `PENDING`, `DEAD`로 전이할 수 있다.
- 발행 실패가 retry 한도 안이면 `PENDING`으로 되돌리고 `nextRetryAt`을 계산한다.
- 발행 실패가 retry 한도에 도달하면 `DEAD`로 전이한다.
- 오래된 `PUBLISHING`은 publisher 중단으로 보고 recovery 대상에 포함한다.
- outbox retry는 dispatch message 발행 보장이고, worker dispatch retry는 vendor 발송 실패 복구다.

### NotificationOutboxStatus

_Enum_

#### Values

- `PENDING`: 발행 대기 또는 재시도 대기
- `PUBLISHING`: publisher가 처리 권한을 획득하고 발행 중
- `PUBLISHED`: Kafka 발행 성공
- `DEAD`: 자동 발행 재시도 종료

### NotificationHistory

_Entity_

#### Rules

- 알림 상태 전이마다 from status, to status, 시각, 사유를 기록한다.
- history-service의 장기 사용자 이력과 다르다.
- 이 history는 알림 한 건의 상태 전이 감사 로그다.
- 저장 구조는 `notification_histories` 별도 collection을 기본으로 한다.
- Notification 현재 상태 변경과 history insert는 같은 MongoDB transaction에서 원자적으로 확정한다.
- 별도 Kafka consumer로 상태 이력만 비동기 적재하는 구조는 현재 상태와 감사 이력의 원자성을 깨뜨릴 수 있으므로 사용하지 않는다.

### RetryFailure

_Value Object_

sender, broker, database, network, application 실패를 retry 정책이 판단할 수 있는 표준 형태로 표현한다.

#### Attributes

- `code`: 내부 표준 실패 코드 또는 외부 실패 코드
- `message`: 실패 메시지
- `source`: 실패 원천
- `category`: 실패 분류
- `statusCode`: 외부 HTTP status code
- `retryAfterMillis`: 외부 시스템이 알려준 재시도 대기 시간

#### Rules

- retry 가능 여부는 error code 문자열 하나가 아니라 `source`와 `category`를 기준으로 판단한다.
- vendor나 broker가 내려준 동적 실패 코드는 보존할 수 있다.

### RetryPolicy

_Domain Service_

#### Rules

- retry 가능한 실패라도 attempts가 maxAttempts에 도달하면 `GiveUp`을 반환한다.
- retry 불가능한 실패는 attempts와 무관하게 `GiveUp`을 반환한다.
- retry 가능하고 한도에 도달하지 않았으면 backoff delay와 함께 `Retry`를 반환한다.
- backoff는 exponential로 증가하고 max delay를 넘지 않는다.

## History Context

### History

_Aggregate Root_

#### Rules

- 사용자별 뉴스, 요약, 알림 결과를 장기 조회할 수 있어야 한다.
- notification-service의 발송 처리 상태와 history-service의 장기 이력은 책임을 분리한다.
- history-service는 장기 조회와 통계 적재를 담당한다.
- notification-service 내부의 NotificationHistory는 한 알림 aggregate의 상태 전이 감사 로그이며, history-service의 장기 사용자 이력으로 대체하지 않는다.
