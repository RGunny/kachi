# 패키지 구조

- 모든 모듈이 따르는 패키지 배치 규칙이다.  
층의 책임과 의존 방향은 [아키텍처.md](아키텍처.md), 코드 모양 관례는 [개발가이드.md](개발가이드.md)에 있다.

```text
me.rgunny.kachi.{service}
├── domain
├── application
│   ├── port
│   │   ├── inbound
│   │   └── outbound
│   ├── service
│   └── exception
├── adapter
│   ├── inbound
│   └── outbound
└── config
```

## application/port

- `inbound`/`outbound`로 쓴다. 
- `<feature>/` 루트에는 어댑터가 구현하는 인터페이스만 두고, 파라미터·리턴 타입은 `<feature>/model/`에 둔다.
  - 예: `port/outbound/sender/NotificationSender.kt`, `port/outbound/sender/model/SendNotificationCommand.kt`.
- `model/`을 종류로 다시 가르지 않는다. 10개를 넘으면 feature를 나눈다.
  - 예: `port/inbound/{admin,dispatch,dlt,outbox,request}/`.
- 여러 포트가 쓰는 타입은 생산자 포트의 feature에 둔다.
- outbox 영속·publisher·serializer 포트는 `outbox/` 하나에 둔다.
  - 예: `port/outbound/outbox/{NotificationOutboxPersistencePort, NotificationDispatchPublisher, NotificationEventSerializer}.kt`.

## application/service·exception

- `service/`는 `port/inbound/<feature>/`와 같은 이름으로 나눈다. 유스케이스가 셋 이하면 평면이다.
  - 예: `service/{admin,dispatch,dlt,outbox,request}/`.
- 서비스 안에서만 쓰는 정책·결과 타입은 그 서비스 옆에 둔다.
  - 예: `service/dispatch/DispatchNotificationPolicy.kt`.
- `exception/`은 평면이다. 모듈 예외·오류 코드 인터페이스·기능별 오류 코드 enum과 예외를 나란히 둔다.
  - 예: ai `application/exception/{AiException, AiErrorCode, AiOutboxErrorCode, AiOutboxPublishException}.kt`.

## domain

- 하위 패키지는 aggregate 하나와 그 VO·enum·정책, 또는 한 외부 연동의 실패 모델이다. 나머지는 평면이다.
  - 예: story `domain/{outbox,inference}/`.

## adapter/inbound

- 1단은 진입 기술이다. 예: `adapter/inbound/{messaging,scheduler,web}/`.
- 스케줄러와 컨트롤러가 함께 부르는 실행기는 기능 이름 패키지에 둔다. 예: collector `adapter/inbound/{collection,outbox}/`.
- 요청·응답 DTO는 컨트롤러 옆에 둔다. 컨트롤러가 넷 이상이면 `request/`·`response/`로 가른다. 예: `web/admin/{request,response}/`.
- 공통 응답 형식은 `web/response/`다. 예: `web/response/{ErrorCode, FieldError}.kt`.
- 경계 전용 예외는 그 경계 아래 `exception/`이다. 예: `messaging/exception/InvalidDispatchMessageException.kt`.

## adapter/outbound

- 1단은 포트 패키지 이름이다. 예: `adapter/outbound/{sender,recipient,idempotency}/`.
- vendor 구현이 여럿이면 포트 아래 vendor 패키지다. 예: `sender/{slack,discord,telegram}/`.
- 한 기술이 포트 여럿을 섬기면 기술 이름 아래 포트 이름이다. Spring Data repository·document는 항상 여기다. 예: `persistence/{dlt,notification,outbox}/`.
- 어댑터끼리만 쓰는 계약·데코레이터·분류기·codec은 1단 패키지 루트다. 예: `sender/{MeteredNotificationSender, VendorHttpExceptionClassifier}.kt`.
- vendor·다른 서비스의 요청·응답 형태 그대로인 타입은 `dto/`다. 예: `sender/telegram/dto/`, `recipient/dto/`.
- 포트 없이 어댑터끼리만 쓰는 부품은 역할 이름 패키지다. 예: `adapter/outbound/monitoring/`.
- 하위 패키지는 포트 이름·vendor 이름·`dto/` 세 종류뿐이다.

## config

- 평면이다. 파일명은 `<기능>Config`·`<기능>Properties`, vendor 조립은 `<Vendor>…Config`다.
  - 예: `config/{NotificationRecipientConfig, NotificationRecipientProperties, TelegramNotificationSenderConfig}.kt`.
- `@ConfigurationProperties`는 `config/`에만 둔다.

## 테스트

- `src/test`는 main 패키지를 미러한다. 예: `sender/telegram/TelegramNotificationSenderTest.kt`.
- test 루트에는 `fake/`(포트 Fake), `fixture/`(고정 시간·테스트 데이터), `support/`(stub 서버 등 시험 도구), `architecture/`(ArchUnit)를 둔다.
- 실제 외부 서버를 부르는 테스트는 `src/realTest`다. 예: story `src/realTest/.../adapter/outbound/tei/`.

## ArchUnit 슬라이스

- 1단 패키지는 순환이 없고, `adapter/outbound` 바로 아래 패키지는 서로 의존하지 않는다.
- 부품을 나눠 쓰는 어댑터는 같은 슬라이스에 둔다. 예: `sender/VendorHttpExceptionClassifier`를 `sender/{slack,discord,telegram}`이 공유한다.
