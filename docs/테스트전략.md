# 테스트 전략

## 테스트 분류

Kachi는 테스트가 실제 인프라에 의존하는지, Spring context를 얼마나 사용하는지에 따라 테스트를 구분한다.

| 분류 | 기준 | 예시 | 파일명 |
| --- | --- | --- | --- |
| Unit Test | 단일 클래스나 함수의 규칙을 검증한다. Spring context와 실제 인프라를 사용하지 않는다. | domain, application service, token helper | `*Test` |
| Slice Test | 특정 프레임워크 계층 일부만 띄워 계약을 검증한다. 실제 DB/Redis는 사용하지 않는다. | `@WebMvcTest`, controller, security filter | `*Test` |
| Integration Test | 둘 이상의 컴포넌트가 실제 인프라와 함께 동작하는지 검증한다. | JPA adapter + MySQL, Redis adapter + Redis | `*IntegrationTest` |
| E2E Test | 외부 클라이언트 관점에서 전체 사용자 시나리오를 끝까지 검증한다. | 회원가입 -> 로그인 -> 토큰 발급 -> 키워드 등록 -> 조회 | `*E2ETest` |

## 파일 배치

기본 테스트 패키지는 production package와 대칭으로 둔다.

```text
src/test/kotlin/me/rgunny/kachi/{service}/...
```

같은 adapter라도 테스트 성격은 파일명으로 구분한다.

```text
UserPersistenceAdapterTest.kt
UserPersistenceAdapterIntegrationTest.kt
```

현재 프로젝트는 계층별 패키지 구조를 유지하고 있으므로, unit/slice/integration 전용 최상위 패키지를 추가하지 않는다. 테스트 성격이 파일명과 annotation, 사용 인프라에서 드러나도록 한다.

## 인프라 테스트 기준

실제 MySQL, Redis, Kafka, MongoDB 같은 인프라가 붙는 테스트는 `*IntegrationTest` 이상으로 작성한다.

인프라 테스트는 다음 조건을 만족해야 한다.

- Testcontainers처럼 테스트가 직접 인프라 생명주기를 제어한다.
- 로컬 개발용 Docker Compose에 의존하지 않는다.
- production 설정 파일의 임시 값을 억지로 재사용하지 않는다.
- 검증 대상 adapter의 실제 저장, 조회, 제약 조건, 원자성 같은 연동 지점을 확인한다.

## Testcontainers 정책

테스트 DB와 인프라 의존성은 Testcontainers로 통일한다.
테스트는 로컬 개발용 Docker Compose가 떠 있다는 전제에 의존하지 않는다.
Docker Compose는 개발자가 서비스를 직접 실행할 때 사용하는 로컬 인프라이고, Testcontainers는 테스트가 필요한 인프라 생명주기를 직접 제어하기 위한 도구다.

`application-test.yaml`은 테스트 공통 설정만 담당한다.
다음 값은 둘 수 있다.

- scheduler 비활성화 값
- 외부 client fake base URL
- test secret, OAuth2 test client 값
- MongoDB UUID representation
- MongoDB auto-index-creation 정책
- JPA `ddl-auto=validate` 같은 schema 검증 정책

다음 값은 두지 않는다.

- `spring.mongodb.uri`
- `spring.datasource.url`
- `spring.data.redis.host`, `spring.data.redis.port`
- `spring.kafka.bootstrap-servers`
- `localhost`에 고정된 테스트 인프라 접속 주소

Spring context를 사용하는 Testcontainers 테스트는 `@ServiceConnection`으로 동적 접속 정보를 주입한다.
`@SpringBootTest`의 context load 테스트도 실제 DB auto-configuration을 유지하는 경우 Testcontainers config를 import한다.
DB auto-configuration을 제외하는 context load 테스트는 해당 테스트가 persistence wiring을 검증하지 않는다는 의도를 명확히 드러내야 한다.
`@DataMongoTest`, `@DataJpaTest` 같은 persistence slice test도 모듈 공통 테스트 설정이 필요하면 `@ActiveProfiles("test")`로 `application-test.yaml`을 사용한다.
annotation `properties`에는 개별 테스트만의 예외 설정을 두고, UUID representation, auto-index-creation, `ddl-auto` 같은 모듈 공통 정책은 test yaml에 둔다.

Docker daemon은 Testcontainers 기반 integration test의 실행 전제다.
Docker를 사용할 수 없으면 테스트는 skip하지 않고 명확히 실패하게 둔다.
CI와 로컬 모두 같은 전제를 쓰면, 로컬에서 누락된 Docker daemon이나 권한 문제가 빠르게 드러난다.

## MongoDB 테스트 정책

MongoDB persistence/integration test는 실제 index 계약을 검증하기 위해 `spring.data.mongodb.auto-index-creation=true`를 사용한다.
`@Indexed`, `@CompoundIndex`, `@CompoundIndexes`로 정의한 unique/index 계약은 테스트 MongoDB에도 생성되어야 한다.
인덱스 생성 오류나 종료 시점 로그를 피하려고 auto-index-creation을 끄지 않는다.

`ai-service`와 `collector-service`는 MongoDB multi-document transaction을 사용하지 않으므로 일반 `MongoDBContainer("mongo:7.0")`를 사용한다.
`notification-service`와 `notification-worker`는 MongoDB transaction을 검증해야 하므로 `MongoDBContainer("mongo:7.0").withReplicaSet()`을 사용한다.

Reactive Mongo 테스트 종료 시점에 `CreateIndexesOperation`의 `Shutdown in progress` 로그가 보인다면, index 정책을 끄는 대신 Spring context와 container lifecycle 순서를 먼저 점검한다.
현재 기준은 Spring Boot가 관리하는 Testcontainers bean을 사용하고, application context 종료 전에 container를 수동으로 중지하지 않는 것이다.

## MySQL / Redis / Kafka 테스트 정책

`user-service` JPA persistence test는 `MySQLContainer("mysql:8.0")`와 `@ServiceConnection`을 사용한다.
schema 생성과 변경은 Flyway migration으로 관리하고, 테스트에서도 `spring.jpa.hibernate.ddl-auto=validate`를 유지한다.
이 설정은 migration과 entity mapping이 어긋나면 테스트 context 기동 시점에 실패하게 만든다.

Redis가 필요한 Spring context 테스트는 Redis Testcontainer를 `@ServiceConnection(name = "redis")`으로 주입한다.
Spring context 없이 adapter를 직접 조립하는 Redis integration test는 Testcontainers의 mapped port를 직접 사용해도 된다.
이 경우에도 localhost 고정 포트나 Docker Compose Redis에는 의존하지 않는다.

Kafka adapter integration test를 추가할 때는 Kafka Testcontainer 또는 Spring Kafka 테스트 인프라를 사용한다.
운영/로컬 `application-local.yaml`의 `localhost:9092`는 테스트에서 재사용하지 않는다.

## 현재 적용

`user-service`는 다음 테스트 기준을 적용한다.

| 대상 | 분류 | 이유 |
| --- | --- | --- |
| Domain / value object | Unit Test | 순수 규칙 검증 |
| Application service | Unit Test | fake port로 유스케이스 규칙 검증 |
| Web adapter | Slice Test | MVC 요청/응답, security, exception 계약 검증 |
| JPA persistence adapter | Integration Test | MySQL 저장, 조회, unique 제약 검증 |
| Redis refresh token adapter | Integration Test | Redis TTL, revoke, Lua 기반 rotation 검증 |
| Application context | Integration Test | MySQL/Redis Testcontainers와 Flyway/schema 검증 포함 |

`collector-service`는 다음 테스트 기준을 적용한다.

| 대상 | 분류 | 이유 |
| --- | --- | --- |
| Domain / value object | Unit Test | 순수 규칙 검증 |
| Collection service | Unit Test | fake port로 provider 결과 병합, 중복 집계, 실패 처리 검증 |
| Web adapter / scheduler | Unit Test 또는 Slice Test | 수동 실행, provider health check, 중복 실행 응답 계약 검증 |
| News provider adapter | Unit Test | 외부 호출은 fake `ExchangeFunction`으로 대체하고 요청 path/query/header와 응답 변환 검증 |
| Mongo persistence adapter | Integration Test | MongoDB 저장, 조회, unique index, document mapping 검증 |

외부 provider 단위 테스트는 실제 Google/Naver/Finnhub API를 호출하지 않는다.
실제 연결 확인은 로컬 실행 후 provider health API로 수행한다.

`ai-service`는 다음 테스트 기준을 적용한다.

| 대상 | 분류 | 이유 |
| --- | --- | --- |
| Domain / value object | Unit Test | 키워드 확장, 뉴스 요약, 실행 기록 규칙 검증 |
| AI application service | Unit Test | fake port로 키워드별 성공/실패 집계, 중복 저장, 빈 입력 처리 검증 |
| Web adapter / scheduler | Unit Test 또는 Slice Test | 수동 실행, 중복 실행 응답 계약 검증 |
| LLM provider adapter | Unit Test | 실제 LLM API를 호출하지 않고 fake `ExchangeFunction`으로 요청 body, timeout, 응답 변환 검증 |
| user/collector client adapter | Unit Test | internal API 요청 path/query와 응답 변환 검증 |
| Mongo persistence adapter | Integration Test | MongoDB 저장, 조회, unique index, document mapping 검증 |
| Application context | Integration Test | MongoDB Testcontainer와 scheduler/client test 설정 포함 |

LLM 연동 테스트는 실제 provider API를 호출하지 않는다.
실제 연결 확인은 로컬 실행 후 provider health 또는 internal smoke API로 수행한다.

`notification`은 다음 테스트 기준을 적용한다.

| 대상 | 분류 | 이유 |
| --- | --- | --- |
| `Notification`, `NotificationOutbox` | Unit Test | 상태 전이, 멱등 호출, 허용되지 않은 전이 차단 검증 |
| `RetryPolicy` | Unit Test | retry/give-up 결정, attempts 한도, exponential backoff 검증 |
| `NotificationSenderRouter` | Unit Test | 채널별 sender 선택, 누락/중복 sender 예외 검증 |
| `RequestNotificationService` | Unit Test | request dedupe, `Notification + Outbox` 생성, 저장 실패 시 dedupe release 검증 |
| `PublishNotificationDispatchService` | Unit Test | outbox claim, publish 성공/실패, stale publishing 회수, retry 한도 검증 |
| `DispatchNotificationService` | Unit Test | dispatch dedupe, `PUBLISHED/RETRY_WAIT` claim, sender 결과별 상태 전이, retry classification 검증 |
| notification-service HTTP/Kafka inbound adapter | Slice Test 또는 Integration Test | 요청 DTO/event를 command로 변환하고 동일 use case를 호출하는 계약 검증 |
| notification-service persistence/Redis/Kafka adapter | Integration Test | MongoDB 저장/조회/CAS, Redis SETNX/TTL, Kafka publish 계약 검증 |
| notification-worker Kafka listener | Integration Test | `notification.dispatch` consume, retryable result의 retry topic 연결, DLT 이동 검증 |
| sender adapter | Unit Test | 실제 vendor 호출 없이 fake exchange/client로 request header/body, 응답 분류, timeout 처리 검증 |

notification 테스트는 다음 원칙을 지킨다.

- core 테스트는 Spring context와 실제 인프라 없이 fake port로 작성한다.
- Kafka retry topic, DLT, Redis TTL, MongoDB CAS처럼 인프라 의미가 중요한 adapter는 Testcontainers 또는 embedded Kafka 기반 integration test로 검증한다.
- 실제 Slack, Discord, Telegram 같은 외부 vendor API는 단위/통합 테스트에서 호출하지 않는다.
- `DispatchFailureClassification.RETRYABLE`은 Kafka retry 대상이고, `NON_RETRYABLE`은 정상 ack 대상이라는 runtime 계약을 listener 테스트에서 검증한다.
- MongoDB transaction을 검증하는 persistence test는 replica set Testcontainer를 사용한다.
- `notification-service`와 `notification-worker`의 Mongo persistence slice test도 `application-test.yaml`의 Mongo UUID representation과 auto-index-creation 정책을 사용한다.

## 실행 명령

모듈별 테스트:

```sh
./gradlew :user-service:test
./gradlew :collector-service:test
./gradlew :ai-service:test
./gradlew :notification-core:test
./gradlew :notification-service:test
./gradlew :notification-worker:test
```

전체 테스트:

```sh
./gradlew test
```

전체 검증:

```sh
./gradlew check
```

실패 모듈을 한 번에 확인해야 하면 다음처럼 실행한다.

```sh
./gradlew test --continue
```
